\section{Introduction}
\label{sec:introduction}

Agent-based models (ABMs) represent a system as a population of autonomous agents that follow
local rules and interact through a shared environment \citep{macal2010tutorial}. Their appeal
is that aggregate patterns, such as an epidemic curve, a segregated city
\citep{schelling1971dynamic} or an unequal wealth distribution, emerge from rules a domain
expert can state and criticise. Their weakness is the cost of answering questions with them.
A single run tells little: a credible study runs many replicates per parameter combination,
explores the parameter space, fits the parameters to data, asks which of them matter, and
reports all of it in a form others can rerun. Each of these steps multiplies the number of
runs, and each is usually assembled by hand around the simulation library.

Python has become a common language for this work, and Mesa \citep{kazil2020mesa,
terhoeven2025mesa3} its best-known ABM framework. Python makes models easy to write and to
connect to the scientific stack \citep{harris2020numpy, virtanen2020scipy}, but per-agent
Python code is slow, and the surrounding tasks (sweeps, calibration, sensitivity analysis,
provenance) are left to the modeller or to separate tools \citep{herman2017salib,
klinger2018pyabc, kwakkel2017ema}. Faster platforms exist in Java and Julia
\citep{luke2005mason, north2013repast, datseris2024agents} and on GPUs
\citep{richmond2023flamegpu}; in Python, mesa-frames trades the per-agent programming model for
vectorised speed \citep{mesaframes}, and Repast4Py distributes a run over MPI processes
\citep{collier2020repast4py}.

\modelly{} is a new framework, written from scratch, that reduces this cost without asking the
modeller to leave Python or to give up agents. Its programming model is compatible with
Mesa's, so a Mesa user is at home from the first line and a codemod migrates an existing Mesa
model's framework calls. A researcher writes the model as plain Python with agents as objects,
rewrites the phases that act on the whole population as array operations where speed matters,
one phase at a time, and gets:

\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Speed without leaving Python.} Agent attributes can live in model-owned
  \code{numpy} arrays (\emph{columns}), identical agents can be counted rather than
  instantiated (\emph{cohorts}), and the framework's inner loops run in compiled C, each with a
  pure-Python twin that gives the same results (\cref{sec:design}). On eight workloads, with
  those phases written as arrays, the column form runs 2.9 to 33 times faster than Mesa~3.5
  (12 times on flocking against Mesa~3.5 given the same KD-tree search) and 4.6 to 42 times
  faster than Mesa~2.3, and changing the insect model's representation to counted cohorts makes
  it 135 times faster than individuals on Mesa~3.5, with the
  lead growing with the population on the grid epidemic and Schelling's model; a Mesa~3.5 model migrated by the codemod, with no phase
  rewritten, runs 1.05 to 2.3 times faster. An ablation that changes one thing per rung
  (framework, compiled runtime, data structure, search algorithm, array representation)
  attributes the large gains to the array representation of the phases
  (\cref{sec:ablation}). Whether the faster forms compute the same model is tested: against
  the author's Mesa~2.3 reference implementations, over 100 seeds per variant, 29 of 67
  statistic--variant comparisons of the faster forms are shown equivalent within a prespecified
  margin of half a standard deviation after Holm correction (63 at nominal significance), and
  48 are shown equivalent within $\pm 5\%$ of Mesa's mean; a trajectory-level study of three
  workloads (whole curves, spatial clusters, time to converge, extinction probability,
  cycle period) finds the faster forms as close to Mesa~2.3 as Mesa~3.5 is
  (\cref{sec:performance}).
  \item \textbf{The whole study in one package.} Parameter sweeps, approximate Bayesian
  calibration, Morris, Sobol and PAWN sensitivity analysis, emulators and history matching,
  provenance manifests, verifiable archive bundles and ODD descriptions \citep{grimm2006odd,
  grimm2020odd} are part of the framework, each a few lines of code, and share one seeding
  discipline, so a study's results do not depend on the executor, the number of workers or the
  order in which runs finish (\cref{sec:workflow}). Each method is checked against problems
  whose answers are known (\cref{sec:reproducibility}).
  \item \textbf{Results others can rerun.} Seeded generators reproduce the standard library's
  random stream; a run's manifest records everything needed to repeat it, and
  \cmd{modelly verify} repeats it and names the first output that differs; a determinism suite
  checks that the bundled examples give the same digests compiled or in pure Python and
  straight or resumed from a checkpoint, and, run on hosted builds of the checkout and of
  the released wheels (Linux x86-64 and ARM64, macOS ARM64 and x86-64, Windows, under
  CPython 3.12, 3.13 and 3.14), that thirteen of seventeen examples give
  bit-identical digests on all fifteen wheel builds (twelve on the nine builds compiled from
  the checkout) and the others agree at ten significant digits
  wherever the suite compares them (\cref{sec:reproducibility}). The paper states each guarantee's scope: determinism on
  one build, numerical agreement across platforms, and bitwise agreement where it holds.
  \item \textbf{Towards large and data-driven studies.} The same model can be split across
  processes with results byte-identical to one process (a check of correctness; its parallel
  speed-up beyond one laptop is not yet shown), run its array phases on a GPU (steps 34 times
  faster than one CPU core at ten million agents), be differentiated for gradient calibration,
  assimilate live observations, couple agents to diffusing fields, be emulated when runs are
  expensive, start from a synthetic population, and be shared as a web page (tested in
  Chromium) (\cref{sec:scale}).
\end{itemize}

\paragraph{What is new.} The methods \modelly{} integrates are established: approximate
Bayesian computation, Sobol and Morris sensitivity analysis, emulation, data assimilation
and Mesa's programming model are all prior work (\cref{sec:related}). The contribution of
this paper is (i) the objects/columns/cohorts architecture, in which the three levels of
storage share one programming model and a model moves between them one phase at a time,
with a stated proposition, and counterexamples, for when a counted population keeps the
individual model's law (\cref{sec:design}); (ii) the integration of model execution,
deterministic experiment scheduling and verifiable artefacts under one seeding discipline,
so that a calibration or a sensitivity analysis is reproducible, resumable and
executor-independent without extra code (\cref{sec:workflow}); (iii) a Mesa-compatible
interface with a measured migration path, on Mesa's own examples (\cref{sec:samecode});
and (iv) tested execution contracts (compiled and pure cores, split runs, GPU backend) whose
guarantees are stated by scope and checked on several platforms
(\cref{sec:reproducibility,sec:scale}). The evidence for (i) is the main empirical work of
the paper: the speed-ups, the ablation that attributes them, and the equivalence and
trajectory studies that test whether the faster forms are the same model.

The rest of the paper situates \modelly{} among existing tools (\cref{sec:related}),
describes its design (\cref{sec:design}) and research workflow (\cref{sec:workflow}),
evaluates its speed and its agreement with Mesa (\cref{sec:performance}) and the correctness
of its methods (\cref{sec:reproducibility}), measures how it scales out and connects to data
(\cref{sec:scale}), sets out the studies it serves (\cref{sec:usecases}), and ends with the threats to the validity of these measurements and the
software's limitations (\cref{sec:threats}).
