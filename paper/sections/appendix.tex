\section{Reproducing the measurements}
\label{app:reproduce}

Every measured table and figure of this paper is generated from data and scripts in the
repository.
The raw output of the agreement study, the GPU comparison, the
weak-scaling runs, the nowcasting tutorial and the Ishigami estimate is in the paper's
\code{data/} folder, and the playbook timings are in \code{benchmarks/playbooks/results/}.

\paragraph{Artifact checks.} Two scripts let a reader check the paper's artifacts without
rerunning its measurements. \code{verify\_artifacts.py} copies \code{tables/} and
\code{figures/} aside, regenerates every table and figure from the data files with the
scripts above (the \code{analyse} commands and the table scripts), reruns the five scripts
that recompute a data file from the code (the Ishigami estimate, the scramblings, the
cohort counterexample, the graph cut, the nowcast), and compares: the 29 tables byte for
byte, the 9 figures pixel for pixel, the 5 data files on their numbers. \code{check\_listings.py}
extracts the three Python listings of the paper and runs each as printed (the ABC listing
against the model module of \code{docs/calibration.md}, which it writes from the
documentation's own code blocks); the ABC listing's output is the posterior quoted in
\cref{sec:validation}. Both pass at the commit of this version, in the development
environment and from a fresh clone in a fresh environment whose dependencies were resolved
from PyPI at the time (CPython 3.14.8, numpy 2.5.4, scipy 1.18.1, pandas 3.1.0, matplotlib
3.11.2; \code{data/clean\_checkout\_check.json}), where every table, figure and data file
regenerated identically and the ABC listing gave the same posterior to four decimals.
These are the author's runs, not an independent party's. One pitfall for a reader: the
editable install of the listing above compiles the C modules into the checkout; a plain
\cmd{pip install .} run from the repository root imports the checkout's uncompiled
sources rather than the installed wheel, so install editable, or run from another
directory. What the two scripts do not do is rerun a timing, an agreement study or a
hosted workflow, which the commands above do.

The playbook runner starts each run in a fresh interpreter, pins it to one core with
\code{taskset}, alternates the implementations over rounds, checks determinism, and writes JSON
results and a Markdown report to \code{benchmarks/playbooks/results/}. The methods, and the
rules a fair comparison must follow, are described in \code{docs/performance.md}.

\paragraph{Provenance of the measurements.} Every measurement of this paper ran on the code of
the tagged release v1.4.2 (commit \code{bf7a225}), compiled on the measurement machine with
GCC~16.2. One session ran, in this order, the timings at the fixed frequency, the GPU, the weak
scaling, the primary agreement studies, the coverage study, the three data scripts, the
100-million-row run, the active-learning comparison, the GPU and differentiable tests, the
browser runs with the pure wheel and the browser's first load, from the checkout at the tag;
then the Mesa~3.5 + numpy and baseline agreement studies and the two replications on new
seeds, from commit \code{e3cfb74}, which differs from the tag only in the paper's own files;
then, at the tag again, the test suite, and the WebAssembly wheel built and every model run
with it in the browser. A last session ran from commit \code{63e7bd9}, whose \code{modelly}
package is the tag's and which adds the Mesa~3.5 + KD-tree flocking implementation and the
scripts for the size sweep and the prior-drawn coverage: the second timing session of every
playbook, which gives \cref{tab:playbooks} (the first, at the tag, is in
\code{paper/data/playbooks\_session1/}), the size sweep and the prior-drawn coverage study; and the commits after it, whose
\code{modelly} package is still the tag's and which add only options to the paper's scripts, ran
the GPU comparison over five rounds, the coverage study at 100 particles, the virus example on
new seeds and the run-by-run comparison of the KD-tree implementation with Mesa~3.5. Each result file records what it ran with: the
playbook, migrated-model, example and agreement files the commit, the machine, the load and the package
versions; \code{assimilation.json}, \code{ishigami.json} and \code{graph\_cut.json} the commit,
date, interpreter and package versions, their \code{+dirty} marking the benchmark results
written earlier in the session, not code; the \code{weak\_*.json} files the interpreter, the
platform and the load, with the commit and the MPI, mpi4py and Dask versions added from the
environment afterwards and marked so; and \code{gpu\_speedup.json} the package versions of
both arms. In these files the package version recorded for \code{modelly-abm} is the stale
metadata of the development environments' editable installs, not the code: every environment
imported \modelly{} from the checkout, which the commit field identifies.
A further session, on 29 October 2026, ran from commits after \code{069f9b4}, whose
\code{modelly} package and determinism tests are still the tag's (no file under
\code{modelly/} or \code{tests/determinism/} has changed since it) and which add the
scripts of these studies and two workflow files: the trajectory study, the ablation, the
interpreter comparison, the end-to-end sweep, the particle-count sweep, the Sobol
scramblings and the cohort counterexample on the same laptop (the three timing scripts at
its default frequency policy, under a load average of 11 to 51), and the hosted runs of
\code{platform-digests.yml} and \code{mpi.yml} (\code{paper/data/platform\_runs.json}
records their commits, dates and outcomes).
The tagged release v1.4.2 is archived by Software Heritage as
\code{swh:1:rel:661000598425e7a9b958b5a679ca1281aa6f6cc3}.

\section{The workloads}
\label{app:workloads}

\paragraph{Choices in the implementations.} For flocking the Mesa~3.5 implementation uses
the legacy continuous space of \code{mesa.space}, which Mesa~3.5 still provides and which
runs this workload 1.6 times faster than the experimental space of Mesa's own example. \modelly{}'s cell-list
variants keep the data structure of Mesa's grids, each cell holding the list of its agents, and vectorise
only the obvious phases. Where a phase searches cells one agent at a time, as Sugarscape's
foragers do, the Mesa implementations and the cell-list variant use the same single-pass
algorithm, so that their comparison is between data structures; the column and mesa-frames
variants find every forager's best visible cell in one array pass and keep only the walk to a
free cell sequential. The four mesa-frames workloads were also timed in wall-clock time with
one polars thread and with all 16 (\code{paper/scripts/frames\_threads.py},
\code{paper/data/frames\_threads.json}): with all threads the grid epidemic takes 1.88~s
against 1.57~s, Boltzmann wealth 1.69~s against 1.44~s and Sugarscape 3.83~s against 2.86~s,
while Schelling's model is 1.4 times faster (2.05~s against 2.84~s); these are single runs,
unpinned, while other jobs loaded the machine (one-minute load average 8.6 at their start),
which penalises the multi-threaded arm. With that caveat, three of the four workloads' data
frames appear too small for parallel execution to pay for its overhead, and Schelling's is
not. Pinned to the four performance cores, five alternating rounds each
(\code{frames\_threads.py --cores 0-3}, \code{paper/data/frames\_threads\_pinned.json}), four
threads were slower than one on every workload: 1.98~s against 1.69~s on the grid epidemic,
3.41~s against 2.86~s on Schelling's model, 2.14~s against 1.82~s on Boltzmann wealth and
5.46~s against 3.78~s on Sugarscape.
