\section{Reproducing the measurements}
\label{app:reproduce}

Every measured table and figure of this paper is generated from data and scripts in the
repository.
The raw output of the agreement study, the GPU comparison, the
weak-scaling runs, the nowcasting tutorial and the Ishigami estimate is in the paper's
\code{data/} folder, and the playbook timings are in \code{benchmarks/playbooks/results/}.

\paragraph{Artifact checks.} Two scripts let a reader check the paper's artifacts without
rerunning its measurements. \code{verify\_artifacts.py} copies \code{tables/} and
\code{figures/} aside, regenerates every table and figure from the data files with the
scripts above (the \code{analyse} commands and the table scripts), reruns the five scripts
that recompute a data file from the code (the Ishigami estimate, the scramblings, the
cohort counterexample, the graph cut, the nowcast), and compares: the 28 tables of
\code{tables/} byte for byte (21 of them in the paper, the other seven the full agreement
tables kept as data), the 9 figures pixel for pixel, the 5 data files on their numbers. \code{check\_listings.py}
extracts the three Python listings of the paper and runs each as printed (the ABC listing
against the model module of \code{docs/calibration.md}, which it writes from the
documentation's own code blocks); the ABC listing's output is the posterior quoted in
\cref{sec:validation}. Both pass at the commit of this version, in the development
environment and from a fresh clone in a fresh environment whose dependencies were resolved
from PyPI at the time (CPython 3.14.8, numpy 2.5.4, scipy 1.18.1, pandas 3.1.1, matplotlib
3.11.2; \code{data/clean\_checkout\_check.json}), where every table, figure and data file
regenerated identically and the ABC listing gave the same posterior to four decimals.
These are the author's runs, not an independent party's. One pitfall for a reader: the
editable install of the listing above compiles the C modules into the checkout; a plain
\cmd{pip install .} run from the repository root imports the checkout's uncompiled
sources rather than the installed wheel, so install editable, or run from another
directory. What the two scripts do not do is rerun a timing, an agreement study or the
digests under several interpreters, which the commands above do.

The playbook runner starts each run in a fresh interpreter, pins it to one core with
\code{taskset}, alternates the implementations over rounds, checks determinism, and writes JSON
results and a Markdown report to \code{benchmarks/playbooks/results/}. The methods, and the
rules a fair comparison must follow, are described in \code{docs/performance.md}.

\paragraph{Provenance of the measurements.} Every measurement of this paper ran on
4 November 2026 from commit \code{6cd4ae6}, whose \code{modelly} package is identical to the
tagged release v1.5.0 (the commit differs from the tag only in documentation and the documentation site's test), compiled on
the measurement machine with GCC~16.2, by \code{paper/measure/measure\_150.sh}. One session
ran, in this order: at the fixed frequency, the first timing session of every playbook
(\code{paper/data/playbooks\_session1/}), the migrated models, Mesa's own examples, the
mesa-frames threads, the three sizes, the ablation, the end-to-end sweep, the three CPython
versions, the ODE timings and the second timing session of every playbook, which gives
\cref{tab:playbooks}; then, at the machine's default frequency policy, the GPU comparison over
five rounds, the weak scaling, the agreement and trajectory studies, the run-by-run comparison
of the KD-tree implementation with Mesa~3.5, the virus example's trace and replications on
new seeds, the calibration studies, the data scripts, the 100-million-row run, the
active-learning comparison, the GPU and differentiable tests, the browser runs with the pure
and the WebAssembly wheel, the browser's first load and the test suite. A second session the
same day, \code{paper/measure/measure\_150b.sh}, wrote the exact digests and ran the
determinism and distributed suites under three interpreters (\cref{sec:reproducibility}).
Each result file records what it ran with: the playbook, migrated-model, example and
agreement files the commit, the machine, the load and the package versions;
\code{assimilation.json}, \code{ishigami.json}, \code{graph\_cut.json} and the other data
scripts' files the commit, date, interpreter and package versions, their \code{+dirty}
marking the benchmark results written earlier in the session, not code; the
\code{weak\_*.json} files the interpreter and the platform; and \code{gpu\_speedup.json} the
package versions of both arms. The tagged release v1.5.0 is archived by Software Heritage as
\code{swh:1:rel:7b7b49f3d26e8411797bb8a29e3c83eff3b98222}.

\section{The workloads}
\label{app:workloads}

\paragraph{Choices in the implementations.} For flocking the Mesa~3.5 implementation uses
the legacy continuous space of \code{mesa.space}, which Mesa~3.5 still provides and which
runs this workload 1.6 times faster than the experimental space of Mesa's own example. \modelly{}'s cell-list
variants keep the data structure of Mesa's grids, each cell holding the list of its agents, and vectorise
only the obvious phases. Where a phase searches cells one agent at a time, as Sugarscape's
foragers do, the Mesa implementations and the cell-list variant use the same single-pass
algorithm, so that their comparison is between data structures; the column and mesa-frames
variants find every forager's best visible cell in one array pass and keep only the walk to a
free cell sequential. The four mesa-frames workloads were also timed in wall-clock time with
one polars thread and with all 16 (\code{paper/scripts/frames\_threads.py},
\code{paper/data/frames\_threads.json}): with all threads the grid epidemic takes 1.68~s
against 1.36~s, Boltzmann wealth 1.54~s against 1.35~s and Sugarscape 3.61~s against 2.88~s,
while Schelling's model is 1.5 times faster (1.81~s against 2.63~s); these are single runs,
unpinned, while other jobs loaded the machine (one-minute load average 7.6 at their start),
which penalises the multi-threaded arm. Pinned to the four performance cores, five
alternating rounds each (\code{frames\_threads.py --cores 0-3},
\code{paper/data/frames\_threads\_pinned.json}), four threads were faster than one on every
workload: 1.15~s against 1.19~s on the grid epidemic, 1.28~s against 2.11~s on Schelling's
model, 0.93~s against 1.13~s on Boltzmann wealth and 2.00~s against 2.41~s on Sugarscape.
Threads therefore pay on Schelling's model and, on cores of their own, modestly on the
other three, whose data frames gain little (4\% on the grid epidemic); under load they cost
more than they gain on those three.
