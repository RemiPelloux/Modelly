\section{Performance}
\label{sec:performance}

A framework can be fast in two senses: the same model code runs faster on it, or it lets a
modeller write the same model in a faster form. We measure both, with methods chosen to make
the comparison fair and repeatable, and check separately that the faster forms compute the
same model. All the comparisons with Mesa are CPU time (\code{time.process\_time}), measured
in-process, pinned to one core with \code{taskset}, with the implementations alternating, on an
Intel Core Ultra 7 356H laptop running Linux, CPython 3.15.0 and numpy 2.5.4 in each
implementation's environment, against Mesa 2.3.2 and Mesa 3.5.1; the pre-commit guard of
\cref{sec:regressions} times short bursts of wall-clock time instead. The core was held at
its 1.9~GHz base frequency (the \code{performance} governor, turbo disabled) for every timing
of this section except the medfly notebook and the release comparisons of
\cref{sec:regressions}, which were timed with turbo enabled. Following
\citet{kalibera2013rigorous}, every run is a fresh interpreter or a fresh model, the rounds are
paired and their order varies, and we report medians with their spread and bootstrap intervals
rather than single runs.

\paragraph{Speed-up.} For a workload with CPU times $T_{r}$ over rounds $r = 1, \dots, R$, we
report
\begin{equation}
  S_{\mathrm{steps}} = \frac{\operatorname{median}_r T^{\mathrm{Mesa}}_{\mathrm{steps},r}}
  {\operatorname{median}_r T^{\mathrm{Modelly}}_{\mathrm{steps},r}},
  \qquad
  S_{\mathrm{total}} = \frac{\operatorname{median}_r T^{\mathrm{Mesa}}_{\mathrm{build},r}
  + \operatorname{median}_r T^{\mathrm{Mesa}}_{\mathrm{steps},r}}
  {\operatorname{median}_r T^{\mathrm{Modelly}}_{\mathrm{build},r}
  + \operatorname{median}_r T^{\mathrm{Modelly}}_{\mathrm{steps},r}},
  \label{eq:speedup}
\end{equation}
where \emph{steps} is the simulation and \emph{build} the construction of the model and its
agents. $S_{\mathrm{steps}}$ is the gain per simulated step, which dominates long runs;
$S_{\mathrm{total}}$ is the gain for one run of the benchmark's length. Round $r$ runs every
implementation on seed $r$, so the per-round ratios are paired.

\subsection{Same code: a port that changes only the framework API}
\label{sec:portability}

A research notebook written for Mesa~2.3, a medfly population model whose main cell runs a
576-season factorial experiment, was ported with \modelly{}'s codemod. The port changes only
the framework API: imports, agent construction, the agent registries, the name of the model's
step method and the seeding line; every line of model logic is unchanged. Both versions are
seeded identically, and their output tables are bit-identical.

The seasons were then run in 48 chunks alternating between two persistent processes, one per
framework, pinned to one core, with every chunk's records hashed and compared (no mismatch in
any run), at 1/30 of the model's full scale. With the port seeding \code{random.Random}, as
Mesa does, \modelly{} took 1.04, 1.02 and 1.02 of Mesa's CPU time in three paired runs (median
1.02, about 2\% slower); with \code{FastRandom}, \modelly{}'s compiled generator, which
reproduces the same stream, it took 1.02, 0.94 and 0.94 (median 0.94, 6\% faster; the first
of these runs shared the machine with other jobs). An early profile of the model, before
its code was optimised (identically in both notebooks), put 68\% of its time in its own code
and 7\% in the framework (\code{docs/performance.md}), so the framework
has little to gain on it; this model is private, so this result can be checked only through the
public ports below.

\paragraph{Two public ports.} The medfly notebook is private, so we repeated the experiment on
the two playbooks of \cref{sec:playbooks} whose Mesa~2.3 implementations use no Mesa~2 grid
(\modelly{} provides cell spaces instead, and porting a grid means rewriting it): the insect
population and Boltzmann wealth. The codemod rewrote imports and constructors; the steps it
reported were done by hand, as its report says (the agents' identifier parameter removed, the
seeding line, which sets \code{model.random} to \modelly{}'s compiled \code{FastRandom} on the
stream Mesa~2.3 draws from, and for Boltzmann wealth Mesa~2.3's random activation, which reshuffles one
persistent order in place each step, kept as an agent set reshuffled in place). The ports,
in \code{benchmarks/ports/}, give the same statistics as the Mesa~2.3 originals on every seed
tried (20 at the small size, 5 at the large), and over ten alternating rounds in fresh
interpreters on one performance core they take 0.22 (insect population) and 0.37 (Boltzmann
wealth) of Mesa~2.3's CPU time, every round within 0.21 to 0.23 and 0.36 to 0.37
(\code{paper/scripts/ports.py}). Profiles
show why: these models spend most of their time in framework calls (Mesa~2.3 rebuilds its
agent set each time \code{model.agents} is read, draws through the standard library's
generator, and collects agent data in a Python loop), and those calls are \modelly{}'s
compiled ones.

\paragraph{Ports from Mesa~3.5.} Code written for current Mesa ports with less effort: five of
the eight Mesa~3.5 playbooks run on \modelly{} after the codemod alone, with no manual step
(\code{benchmarks/ports\_mesa3/}). The other three do not: flocking uses Mesa's legacy
\code{mesa.space.ContinuousSpace}, and predator-prey and Sugarscape use Mesa~3.5's property
layers, neither of which \modelly{} implements. The five ports take 0.45 (Boltzmann wealth),
0.51 (insect population), 0.74 (grid epidemic), 0.86 (network contagion) and 0.93
(Schelling's model) of Mesa~3.5's CPU time, medians of ten alternating rounds whose per-round
ratios span 0.42--0.46, 0.46--0.54, 0.68--0.78, 0.84--0.89 and 0.90--0.96. Their outputs are not
bit-identical to Mesa~3.5's, because \modelly{} derives \code{model.random} from the seed in a
different way, so we compared them in distribution as in \cref{sec:agreement}: over 100 shared
seeds at the small size, 24 of the 26 statistics are equivalent within $0.5\,s_p$, two paired
$t$-tests fall below 5\% before correction (the network's peak of infections and the Boltzmann
model's largest wealth, $|d| \le 0.31$) and none after it, and no Kolmogorov--Smirnov test does.
\paragraph{Mesa's own examples.} The ports above are of implementations we wrote. Mesa~3.5
ships ten example models written by its developers, and we ported copies of them,
kept in \code{benchmarks/mesa\_examples/}: eight run on \modelly{} after the codemod and one more edit
to each, the import of the example's own agents made relative (the codemod points it at
\modelly{}'s bundled example of the same name), plus, for the Epstein civil-violence model, the
one step its report asks for (\code{self.steps} becomes \code{self.time}); Sugarscape G1MT uses Mesa's property layers and
alliance formation its meta-agent factory, which \modelly{} lacks. Porting them found a gap in
the codemod, which rewrote three Mesa~3.5 module paths to \modelly{} paths that do not exist
without reporting them; the codemod now maps them and reports any module without an
equivalent (the fix is in the next release; the timed code does not import the codemod). We ran
each original and its port at Mesa's default parameters, or, where the defaults run in well
under 0.2~s, on a larger grid at the same density (the virus model on 1,000 nodes), for ten alternating rounds on the same
fixed-frequency core, and compared every model reporter, at the last step and averaged over
the run, over 100 shared seeds. \Cref{tab:mesa-examples} gives the results: the ports take
0.61 (wolf--sheep) to 0.96 (boid flockers) of Mesa~3.5's CPU time, and all 35 statistics are
equivalent within $0.5\,s_p$, with no paired $t$-test or Kolmogorov--Smirnov test below 5\%
even before correction.

notebook, to 1.6 times on Mesa~3.5's own examples and 2.7 and 4.6 times on Mesa~2.3 models,
whose framework calls are slower; the larger gains come from the forms of \cref{sec:playbooks}.

\subsection{Each framework's own idiom: eight playbooks}
\label{sec:playbooks}

Eight workloads, chosen to exercise different parts of an ABM framework, are each implemented
at least twice: an SIR epidemic on a grid, predator-prey with grass, flocking
\citep{reynolds1987flocks}, a contagion on a network, a stage-structured insect population,
Schelling's segregation model \citep{schelling1971dynamic}, Boltzmann wealth exchange
\citep{dragulescu2000statistical} and Sugarscape \citep{epstein1996growing}. Each has two
reference implementations written the way Mesa's API intends: one for Mesa~2.3 (per-agent
methods on its grids, continuous space and network space) and one for the current Mesa~3.5
(its cell spaces, \code{CellAgent}, \code{AgentSet.shuffle\_do} and its network space, as in
Mesa's own examples, and for flocking \code{mesa.space.ContinuousSpace}, which Mesa~3.5 still
provides and which runs this workload 1.6 times faster than the experimental space of Mesa's
example), both plain per-agent Python. Four workloads (the grid epidemic, Schelling's model,
Boltzmann wealth and Sugarscape) also have a \emph{mesa-frames} implementation
\citep{mesaframes}, vectorised over polars data frames the way that library's examples write
models: it is the vectorised Python competitor to \modelly{}'s columns. Three workloads (the
grid epidemic, Schelling's model and Boltzmann wealth) have a \emph{Mesa~3.5 + numpy}
implementation, the hand-vectorised baseline: a \code{mesa.Model} that owns the population as
numpy arrays, with no \code{Agent} objects, and keeps Mesa's grid for its neighbour table and
property layers and Mesa's \code{DataCollector} for the records. It is what an expert gets by
giving up agent objects altogether, and so a bound on what a framework that keeps them can
reach. The \modelly{}
implementation uses column state, \code{CellIndex}, KD-tree queries or cohorts. Four workloads
have a further \modelly{} variant, \emph{cell lists}, which keeps Mesa's data structure (each
cell holds the list of its agents) and vectorises only the obvious phases. Where a phase
searches cells one agent at a time, as Sugarscape's foragers do, the Mesa implementations and
the cell-list variant use the same single-pass algorithm, so that their comparison is between
data structures; the column and mesa-frames variants find every forager's best visible cell in one
array pass and keep only the walk to a free cell sequential. Every implementation agrees with
Mesa~2.3 (\cref{sec:agreement}), and three Mesa~3.5 implementations, which draw the same
random numbers in the same order, reproduce it run by run: flocking, the network contagion and
the insect population. Each
implementation is run twice from the same seed and must reproduce its own output exactly; all
do. \Cref{tab:workloads} in the appendix gives every workload's parameters. All variants of all
workloads were timed in one session, ten rounds each, on one performance core, the order of
the variants rotating from round to round; each result file records the commit, the date, the
load, the core and its power policy, and every package version. With the frequency fixed,
every per-round ratio over Mesa~2.3 lies within 15\% of its median (over Mesa~3.5, within
17\%), and for 24 of the 28 timed variants within 10\%, although other jobs shared the machine (one-minute load average 3.0 to 21.8 at the start of
each workload); \cref{tab:speedup-ci} in the appendix gives a bootstrap 95\% interval for every
speed-up, resampling the paired rounds.

\paragraph{Where \modelly{} is fast, and why.} \modelly{}'s column form runs every workload
faster than Mesa~2.3 and Mesa~3.5, and faster than mesa-frames on the four it implements
(\cref{tab:playbooks,fig:speedups}): its steps run
4.6 to 45 times faster than Mesa~2.3, 2.9 to 33 times faster than Mesa~3.5 and 3.0 to 9.4 times
faster than mesa-frames, and its cohort form runs the insect population 243 times faster than
Mesa~2.3 and 133 times faster than Mesa~3.5. \Cref{tab:why} gives the reason workload by
workload. In each, one \modelly{} mechanism replaces a Python loop over the agents with a few
array operations over the whole population: a column read or write instead of an attribute per
agent, one count over the grid's adjacency instead of a neighbourhood walk per agent, one
KD-tree query instead of a distance test per pair, one sparse product over a network instead of
a loop over each node's neighbours, one binomial draw per class instead of one draw per insect.
The gain therefore grows with the share of a step that such a mechanism covers: largest where
every phase becomes array work (flocking, the grid epidemic, Schelling's model, the network),
smaller where a phase must stay sequential, as the foragers' walk to a free cell in Sugarscape,
or where the step creates and removes many agents, as the births and deaths of predator-prey
and of the individual insect model, or where a cost every implementation shares dominates the
step, as Boltzmann wealth's data collector, which records the Gini coefficient and every
agent's wealth after each step (\cref{sec:threats}). Code that gives up agent objects
altogether goes further still: hand-written numpy is 1.8 to 4.4 times faster than the columns
(below). The arguments that each vectorised phase has the law of its
per-agent loop are given in the documentation (\code{docs/vectorised\_phases.md}), and
\cref{sec:agreement} checks that the outputs agree.

\paragraph{The other implementations.} Mesa~3.5 is faster than Mesa~2.3 on five workloads
(1.3 to 3.1 times), as fast on flocking and Sugarscape, and slower on predator-prey (0.91
times). mesa-frames is 2.1 to 6.5 times faster than Mesa~2.3 on three of its four workloads and
slower on Sugarscape (0.71 times), where its per-forager search is a cross join and a sort over
up to about 130,000 rows per step. \modelly{}'s cell-list variants, which keep Mesa's per-cell
agent lists, give 1.3 to 14 times over Mesa~2.3 and 1.3 to 11 over Mesa~3.5: large for
Schelling's model, whose residents mostly count their neighbours, small where movement and
search stay per agent. Construction is where \modelly{} spends more than Mesa~2.3 (it
allocates the columns and indexes the space; Mesa~3.5's cell spaces cost about as much, 0.31
to 0.43~s on the three large grids and the network), so the column form's gain including construction is
4.0 to 32 times, and lower than per step on short runs such as the network contagion (39 times
per step, 10 in total).

\paragraph{Against hand-written numpy.} The Mesa~3.5 + numpy baseline is faster than
\modelly{}'s columns on all three of its workloads: its steps take 0.035~s against 0.157~s on
the grid epidemic (4.4 times faster, 95\% interval 4.3 to 4.6), 0.116~s against 0.205~s on
Schelling's model (1.8 times, 1.7 to 1.8) and 0.121~s against 0.335~s on Boltzmann wealth (2.8
times, 2.7 to 2.8; there partly because it records the wealth as one array per step rather than
as per-agent rows). It pays for that with the model's structure: no agent has an identity,
methods or attributes of its own, the population cannot hold agents of several kinds, every
neighbourhood is a hand-built index table, and every phase has to be rewritten as array
operations before the model runs at all, whereas \modelly{} keeps agent objects, agent sets and
spaces next to the columns, and lets a model be vectorised one phase at a time. Its agreement
with Mesa~2.3 is that of the other implementations (\cref{tab:agreement-mesa3np}: 13 of 14
statistics equivalent within $0.5\,s_p$). One paired $t$-test, Schelling's segregation
($d = 0.24$, 0.6\% of the mean), falls below 5\% after the Holm correction over its 14
comparisons; but on these 100 seeds its Schelling runs give exactly the statistics of the
column variant, whose same difference does not survive the correction over 67 comparisons and
is absent at 300 seeds (\cref{tab:agreement-schelling300}), so it is a fluctuation of these
seeds, not of the implementation. The harness's own six-seed check flags four of its six grid
epidemic statistics (Welch $p = 0.005$ to $0.014$); over 100 seeds at the same small size the
lowest paired $p$ of the grid epidemic is 0.13, and over 100 seeds at the timed size
(\code{paper/data/agreement\_large\_grid\_mesa3np.json}) none has a paired $t$ or
Kolmogorov--Smirnov $p$ below 5\%, the largest $|d|$ is 0.20, and all six are equivalent
within $0.5\,s_p$, so the flags came from six seeds. The gap is the
price of the framework layer: \modelly{} sits between per-agent Mesa and hand-written arrays,
3.4 to 27.5 times above the first and 1.8 to 4.4 times below the second on these three workloads.

\paragraph{mesa-frames with more threads.} polars runs multi-threaded by default, while the
timings above set \code{POLARS\_MAX\_THREADS=1} so that every implementation uses one core. We
also timed the four mesa-frames workloads in wall-clock time with one thread and with all 16
(\code{paper/scripts/frames\_threads.py}, \code{paper/data/frames\_threads.json}): with all
threads, the grid epidemic takes 1.73~s against 1.52~s, Boltzmann wealth 2.61~s against 1.46~s
and Sugarscape 4.29~s against 2.96~s, and only Schelling's model gains (2.12~s against
2.90~s). These runs were unpinned while other jobs loaded the
machine (one-minute load average 23.7 at their start), which penalises the multi-threaded arm;
with that caveat, the data frames at these sizes appear too small for parallel execution to pay
for its overhead, so the single-threaded comparison is unlikely to handicap mesa-frames.

\subsection{Do the faster forms compute the same model?}
\label{sec:agreement}

The implementations draw their random numbers in different orders, so their dynamics cannot
agree run by run; they must agree in distribution. Where two implementations draw the initial
state the same way, a seed gives both the same start: strongly in Sugarscape (correlation
between the two implementations' outputs on a seed $r = 0.91$ to $0.99$) and Schelling's model
($0.42$ to $0.70$), completely in flocking, whose dynamics are deterministic once it has
started ($r = 1$). The comparisons are therefore paired, seed by seed. We ran the Mesa~2.3
reference and every \modelly{} variant of every playbook on the same 100 seeds at the playbook's
small size (2,100 runs), and compared each of the 67 pairs of a summary statistic and a \modelly{} variant (epidemic peak
and final size, final populations, cluster counts, Gini coefficient, and so on) with the Mesa
reference in three ways: a paired $t$-test on the seed-by-seed differences, the two-sample
Kolmogorov--Smirnov test on the two marginal distributions, and paired two one-sided tests
(TOST) of equivalence \citep{schuirmann1987comparison, lakens2017equivalence} with a margin of
half a pooled standard deviation $s_p$, that is, against the null hypothesis
$|\mu_{\mathrm{Modelly}} - \mu_{\mathrm{Mesa}}| \ge 0.5\, s_p$. We report the standardised
difference $d = (\bar x_{\mathrm{Modelly}} - \bar x_{\mathrm{Mesa}}) / s_p$ with its paired 95\%
interval, and correct for the 67 comparisons with Holm's procedure \citep{holm1979simple}.
\Cref{tab:agreement-all} in the appendix lists every comparison.

\Cref{tab:agreement} and \cref{fig:agreement} give the results. The main evidence is the
equivalence test: within the margin of $0.5\,s_p$, 63 of the 67 comparisons are equivalent at
the 5\% level (60 of 64 outside flocking, whose three agree trivially), and 29 when the TOST
$p$-values are Holm-corrected too; the count depends on the margin, 50 at $0.4\,s_p$, 27 at
$0.3\,s_p$ and 19 at $0.25\,s_p$. No difference survives the Holm correction for either test
(the smallest corrected paired $p$ is 0.21), but that is weak evidence on its own: at the
corrected level a paired test on 100 seeds detects $d = 0.33$ with probability 0.13 and
$d = 0.5$ with probability 0.52, for uncorrelated pairs (more where the shared initial state
correlates them). Before correction, six paired $t$-tests and three
Kolmogorov--Smirnov tests fall below 5\%, against 3.2 expected by chance for each test among the 64
comparisons outside flocking if the tests were independent (they are not: the statistics of a
workload are related, such as its final S, I and R). Every $|d|$ is at most 0.33, and every
difference of means at most 11\% of Mesa's; six intervals exclude zero, so
these are small but, taken one at a time, detectable differences: three in Schelling's model
($|d| \le 0.24$, at most 4.3\% of the mean, made detectable by the shared initial state), the mean
sheep population of predator-prey with cell lists, the final adult count of the individual
insect model and the share of agents without wealth in the Boltzmann model ($|d| \le 0.33$, at
most 1.4\%). The spreads agree too: the ratio of the two implementations' standard deviations
lies between 0.77 and 1.27, and one median-centred Levene test \citep{brown1974robust} of 67 falls below 5\%, none after the Holm
correction, so no vectorised phase changes the variability of an outcome. The earlier check shipped with the benchmark harness, six seeds
and an unpaired Welch test \citep{welch1947generalization} at 1\%, could not have shown any of
this: its power to detect a difference of one standard deviation is 13\%.

\paragraph{At the timed size.} We repeated the study at the large size used for the timings,
with 50 seeds per variant (1,050 runs; \cref{tab:agreement-large}). Again no difference
survives the Holm correction; before it, one paired $t$-test (Sugarscape with cell lists, mean
wealth, $d = 0.11$, 0.3\% of the mean) and two Kolmogorov--Smirnov tests fall below 5\%, and
53 of the 67 comparisons are equivalent within the margin, fewer than at the small size because
half as many seeds give wider intervals. The largest differences were in the grid epidemic's
peak time, about 11\% later in both \modelly{} variants ($d = 0.43$ and $0.40$, paired
$p = 0.05$ and $0.07$). Rerun with 200 seeds, they vanish: no interval of the twelve grid
epidemic comparisons excludes zero, the largest $|d|$ is 0.15 (the peak time's is 0.08 and
0.10, 2\% of the mean), and all twelve are equivalent within $0.4\,s_p$, also after the Holm
correction.

\paragraph{The other baselines against Mesa~2.3.} The same study on the Mesa~3.5 and mesa-frames
implementations, 100 seeds at the small size (2,000 runs), checks that the other baselines
compute the same models (\cref{tab:agreement-baselines}). All 40 Mesa~3.5 statistics are
equivalent within $0.5\,s_p$, no paired $t$-test or Kolmogorov--Smirnov test falls below 5\%
even before correction, and the largest $|d|$ is 0.24. Of the 20 mesa-frames statistics 18 are
equivalent and the largest $|d|$ is 0.31; five of its paired $t$-tests fall below 5\% before
correction, and its Schelling implementation ends slightly more segregated than Mesa~2.3's,
a difference that survives the Holm correction over the 60 comparisons ($p = 0.013$). Rerun over 300 seeds (\cref{tab:agreement-schelling300}), the

\subsection{No measurable regression between releases}
\label{sec:regressions}

Performance work regresses easily: a clearer error message or a thread-safety guard on a hot
path costs a few percent that no single test notices. From release 1.3.1 on, every release is
benchmarked against the previous published one before it is tagged, using wheels built by the
same toolchain and identical dependencies, on three measurements in paired alternating runs:
14 core operations (agent sets, column reads and writes, agent and column removal, cell
moves, data collection, events, random draws) plus a \code{numpy}-only control
that must read 1.00, the eight playbooks seed by seed, and the medfly notebook at 1/30 of its
full scale, chunk by chunk. A release ships only if none shows a measurable regression, by the
criterion below, whose 3\% tolerance lets a smaller slowdown pass. Release 1.3.1 was compared with 1.2.0, the last release before the
regressions that 1.3.0 introduced. Between releases, a
pre-commit hook (\cmd{python -m modelly.dev install-hooks}) times the core operations of the
working tree against the last release in about ten seconds, and refuses a commit when an
operation is measurably slower: its median time ratio above 1.03 and the lower quartile of the
ratios above 1.00, confirmed by re-timing it with three times as many pairs.

The release benchmark found slowdowns. Release 1.3.0, published before the policy
existed, had made a column read 2.5\% slower, below the gate's 3\% tolerance but visible in the
release benchmark's longer runs, and removed anyway (the getter had started to capture the column's name for a clearer
error), and, on regular builds, the neighbourhood walk and the cell move paid for
free-threading safety they did not need; 1.3.1 removed both. Against 1.2.0, 1.3.1 takes 0.80
of the time on \code{select}, 0.88 on \code{agg}, 0.94 on agent creation and removal and 0.98
on \code{shuffle\_do}, 0.99 to 1.01 (within noise) on the other operations (medians of five
paired sessions), 0.87 to 1.04 on the playbooks (medians of five paired rounds, identical
outputs), and 1.00 on the medfly notebook at 1/30 scale (17.92~s and 17.92~s, identical
records). Release 1.3.2, whose only change to the library is the ABC-SMC correction, passed
the same gate against 1.3.1: no core operation slower by the criterion; playbook ratios between
0.96 and 1.04 over five rounds, and 0.99, 1.01 and 1.07 for the three noisiest re-timed over 15
rounds (lower quartiles 0.97 to 0.99, so not slower by the criterion), with identical outputs;
and a paired ratio of 0.98 on the notebook (per-round ratios 0.87 to 2.15, so that arm detects
only large regressions) with identical records. The playbooks run no code
that changed: the compiled modules' machine code is identical to 1.3.1's. The playbook arm therefore
shows the gate's noise floor: its per-round ratios spread by more than 3\%, so a median of 1.07
passes while its lower quartile is below 1, and slowdowns of a few percent are detected only
by the core operations' longer, tighter measurements. The raw numbers of both release
comparisons are in \code{paper/data/release\_gates.json}, except the notebook timing of
1.3.1 against 1.2.0, whose raw output was not kept.
