\section{Threats to validity and limitations}
\label{sec:threats}

\subsection{Threats to the validity of the measurements}

\paragraph{The baselines.} The playbooks compare against Mesa~2.3.2 and Mesa~3.5.1 (3.5.2 followed on 28 October 2026); Mesa~2.3 runs here on CPython
3.15, which it does not officially support. The Mesa~3.5 and mesa-frames implementations were
written for this paper, following each library's documentation and examples, and their
developers might write them faster. mesa-frames was measured from its development branch
(commit \code{ef92326}, reporting version 0.1.1.dev0, polars~2.0, on one thread), on four of the eight workloads; writing
the others needs features it lacks (it has no continuous or network space), and working
around three defects we met (neighbourhoods on a torus, the removal of agents, and
neighbourhoods of radius above one) made its code longer than its examples. AgentPy,
Agents.jl and NetLogo have not been measured, and the speed-ups should not be read as applying
to them.

\paragraph{Framework or algorithm.} The playbook speed-ups measure what a modeller gains by
writing each model in the form the framework offers, not the framework's overhead alone, and
part of a gain can be algorithmic: the Mesa flocking implementation scans every agent for
neighbours, as Mesa's continuous space does, while the \modelly{} one queries a KD-tree.
\Cref{sec:ablation} separates these by changing one thing per rung on four workloads; the
KD-tree baseline there gives the same statistics as Mesa~3.5's own search on all 110 seeds
compared (\code{paper/data/flocking\_kdtree.json}). What the ablation does not separate is
the vectorised rewrite of a phase from the column storage that makes it possible, since the
one requires the other; the Mesa~3.5 + numpy baseline, which has the arrays without the
framework, bounds that from the other side.

\paragraph{What the timings include.} The timed region is the whole simulation, including the
data collection and the summary statistics of each workload. In the Boltzmann wealth model the
data collector (the Gini coefficient and the wealth of each of 10,000 agents, every step) is a large part of every
implementation's run, so that workload measures data collection as much as the exchange; all
implementations compute the Gini coefficient with \code{numpy}, the per-agent Mesa ones after
gathering the agents' wealth in a Python loop. The summaries computed after the last step are a
small part of each run (about 2\% of Mesa's Schelling run).

\paragraph{Who wrote the implementations.} Every implementation of every playbook, the Mesa ones
included, was written by the author of \modelly{}, and no independent party has yet
reviewed them or rerun the benchmarks. Each Mesa version follows Mesa's documented API and
examples, and all of them are in the repository for inspection. One baseline invites a closer look: our Mesa~3.5 predator-prey, which
follows Mesa's own examples (\code{CellAgent} on an \code{OrthogonalMooreGrid}, grass in a
property layer), runs slower than Mesa~2.3's (0.92 times); we have not profiled why, so the
columns' 6.9 times over Mesa~3.5 there may be larger than a tuned Mesa~3.5 model would allow. What a third party can check without rerunning the timings is
that every table and figure regenerates from the published data and that every listing
runs as printed: \code{paper/scripts/verify\_artifacts.py} and
\code{paper/scripts/check\_listings.py} do both, and both pass at the commit of this
version (\cref{app:reproduce}). The one comparison whose
baselines we did not write is that of Mesa~3.5's own examples (\cref{tab:mesa-examples}),
whose Mesa arm runs Mesa's code unmodified; it measures the same-code gain, not the gain of the faster
forms, which no Mesa-written model can show.

\paragraph{Measurement.} The timings of the playbooks, the migrated models and Mesa's examples come from
one laptop with a hybrid processor, pinned to one performance
core (CPU 2, one of the processor's four 4.7~GHz
cores; the other twelve are efficiency cores), under the \code{intel\_pstate} driver with the
\code{performance} governor and turbo disabled, so the core ran at its 1.9~GHz base frequency.
Absolute times are therefore longer than on a turbo-enabled machine; the ratios are what we
report. The core was pinned but not isolated: other work shared the machine (one-minute load
average 2.3 to 3.9 at the start of each workload of the main timings, 4.2 at the start of the
size sweep), and \code{taskset} pins the benchmark, not the other processes, so under load
they can run on the same core; CPU time excludes their time but not their cost in context
switches, and they compete for the shared cache and memory bandwidth, which may weigh more on the
memory-bound array code than on interpreter-bound per-agent code. The order of the
implementations rotated from round to round: every per-round ratio over Mesa~2.3 lies within
17\% of its median (over Mesa~3.5, within 17\%), for 28 of the 29 non-reference variants
within 10\% (the exception is the insect population's column form, 16\%), and the bootstrap
intervals of \cref{tab:speedup-ci} are a few percent wide (42.1 [41.7, 42.5] for the grid
epidemic's columns over Mesa~2.3). Those are within-session intervals; between sessions we timed all
eight playbooks twice, in two sessions on the same core and settings
(\code{paper/data/playbooks\_session1/} and \cref{tab:playbooks}), and every one of the 50 speed-ups the two
sessions share agrees within 7\% (median 1.2\%). The conclusions rest on that one machine: other processors, with other cache sizes and
vector units, will give other ratios. The other measurements of \cref{sec:scale} were
made on the same laptop without the fixed frequency: the GPU comparison has five rounds and
the browser's first load is a median of three, while the weak scaling (\cref{tab:scaling}),
the 100-million-row run and the nowcast are single runs; the claims that carry weight there
(identical outputs, a 28-fold speed-up, shortfalls by a factor) do not turn on a few percent.

\paragraph{One machine, three interpreters, few sizes.} Every timing of \cref{tab:playbooks}
ran on CPython~3.15 on one laptop; \cref{sec:python-versions} repeats the Mesa~3.5 and
column arms on CPython 3.12 and 3.14 on the same machine, where the speed-ups hold to
within the session's noise, but no second processor was measured. The ablation, the
interpreter comparison and the end-to-end sweep (\cref{sec:ablation,sec:python-versions,sec:sweep}),
and the differential equations of \cref{sec:agentode}, ran in the same
session as the main timings, at the same fixed 1.9~GHz on the same core, but each in its own
script with its own rounds, so their ratios are paired within each script. The playbooks are timed
at one population size each, and three of them at three sizes (\cref{tab:sizes}), where the
columns' lead grows with the population; the other five were not timed at other sizes, and
the GPU measurement shows how strongly a speed-up can depend on the size (\cref{sec:gpu}).

\paragraph{Agreement.} The agreement study (\cref{sec:agreement}) compares chosen summary
statistics; the trajectory study (\cref{sec:trajectories}) adds whole curves, spatial
clusters, neighbourhood composition, time to converge, extinction probability and cycle
period on three playbooks, not on all eight and not at the timed size. Six small
differences are individually detectable at the small size, and one more (the columns'
epidemic peak, 3.3 steps earlier) in the trajectory study; that none survives the
correction is weak evidence on its own, since at the corrected level a paired test on 100
seeds detects $d = 0.33$ with probability 0.13 and $d = 0.5$ with probability 0.52 for
uncorrelated pairs (more where the shared initial state correlates them), which is why
the paper reports intervals and equivalence tests rather than the absence of significant
differences. At the timed size the study uses 50 seeds (200 for the grid epidemic), whose
intervals are wider. An equivalence margin of half a standard deviation is a convention,
not a scientific tolerance: it is a medium effect by Cohen's scale, the margin is estimated
from the same data, which makes the test slightly liberal, stricter margins give fewer
equivalences (27 of 67 at $0.3\,s_p$, 19 at $0.25\,s_p$), and the Holm-corrected count
(29 of 67) is the one that controls the familywise error. The science-specific margins of
the trajectory study are prespecified but ours: another modeller may need a tighter
tolerance on a peak's timing than $\pm 2$ steps, and at that margin 100 seeds do not
decide the question for any implementation, Mesa~3.5 included.

\paragraph{Reproducibility.} For this version the determinism suite, the split-run checks,
MPI and the exact digests ran on one machine, Linux x86-64, under CPython 3.12, 3.14 and
3.15, compiled and pure (\cref{tab:determinism}); on it every example gives one exact digest
under all six builds. macOS, Windows and ARM were not run beyond the release workflow's
import of each wheel, nor were the published wheels, so the bitwise and even the ten-digit
agreement across operating systems and architectures is untested for this version, as are
MS-MPI, bundles verified across platforms, the free-threaded wheels and the free-threaded
build of the event heap, the Ray backend and Apple Metal; the golden digests cover ten
steps of seventeen examples (the fourteen bundled examples and three split-run models,
distinct from the zoo). Seven of these pass through transcendental functions or BLAS
reductions whose last bits depend on the platform's libraries, so their exact digests can
be expected to differ on other platforms: a study that needs bitwise agreement across
machines must avoid these operations, or state its guarantee at ten significant digits, as
the suite does. The suite has not been run for more than ten steps.

\paragraph{A young project.} \modelly{} was first released on 24 October 2026, by one developer,
who is so far the only maintainer; the other projects of \cref{tab:features} have been in use
for between two and twenty-seven years.
Every public name carries a stability level, stable or provisional
(\code{docs/api\_stability.toml}); the research workflow and the capabilities of
\cref{sec:scale} are recent, and the latter have been used by their tests and tutorials, not
yet by a study outside the repository. The project's governance is set out in its repository:
issues and pull requests on GitHub, with a contribution guide (\code{CONTRIBUTING.md}), a code
of conduct and a security policy; a stable name keeps working for at least one minor release
after it is deprecated, with a warning naming its replacement, and is removed only in a major
release (\code{docs/deprecations.md}), which no release has yet been, so the notice before a
removal is counted in major releases; releases are tagged after lint, type checks and the test
suite pass. The plugin interface (its entry-point groups, the \code{Plugin} class and its
loader) is frozen for the 1.x series, and \cmd{modelly migrate --check-2.0} lists, with the
line, every change a project must make before 2.0.

\subsection{Limitations of the software}
\label{sec:limitations}

\begin{itemize}[leftmargin=*,itemsep=2pt]
  \item \textbf{Speed comes from the model's form.} A model written agent by agent gains only
  where the framework's own calls take its time (1.05 to 2.2 times over Mesa~3.5, 2.6 and 4.8 over Mesa~2.3, \cref{sec:samecode}); the
  large gains of \cref{sec:playbooks} require phases that can be
  expressed over the whole population. Sequential decisions where each agent depends on the
  previous one's move remain per-agent loops.
  \item \textbf{Scaling out has conditions.} A split run needs per-agent streams and a model
  that meets the contract of \cref{sec:split} (phases with a declared radius, no model-level
  draws, no column or dataset agents, no events of its own), and on one laptop it gains
  little; the GPU backend is slower at 20,000 agents and faster at ten million, the
  crossover unmeasured, and does not pay for cohort tables or for construction; gradients through discrete choices are approximations; fields
  need orthogonal grids with uniform spacing; the Ray backend and Apple Metal are untested.
  \item \textbf{Equations and pairing.} Only the RK45 and RK23 pairs integrate each agent with
  its own steps; stiff systems go through one stacked call whose step all agents share, and the
  stochastic schemes take diagonal noise only. Common random numbers reduce the variance of a
  comparison only while the strategies consume the random numbers in the same number and
  order; an intervention that changes either (a new cohort row, a different branch) loses the
  gain, which \code{treatment\_effect} measures rather than assumes. Language-model agents
  reproduce a run only from their cache of replies.
  \item \textbf{Checkpoints and closures.} Checkpoints pickle the model; models that hold
  lambdas, nested functions, classes created at run time or open files cannot be saved: lambdas
  and nested functions are refused with an error naming them, other unpicklable objects fail
  with pickle's own error. Checkpoints load only under the \modelly{} and the
  Python minor versions that wrote them.
\end{itemize}
