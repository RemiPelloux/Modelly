Performance audit#

This page records how Modelly’s core data structures were audited, what was measured, what changed, and what is still on the table. Numbers come from the benchmark configurations in benchmarks/configurations.py (“large” sizes) and from micro-benchmarks run on the same machine, best of several alternating before/after runs, measured in CPU time.

The question#

Modelly keeps one Python object per agent and stores collections of them in dictionaries: AgentSet was a weakref.WeakKeyDictionary, the model registry is a plain dict, and a cell holds a list of the agents standing on it. Is that the right shape, and where does the time go?

The short answer: the shapes are right for the operations a simulation performs (ordered membership, O(1) removal, stable shuffles), but four things around them were costing far more than the containers themselves. Those were fixed. The one structural change with a large constant factor (columnar agent state) is a roadmap item, not a patch.

What the profile showed#

Profiling the four benchmark models at their “large” configuration put the framework’s own overhead in five places, in order of cost:

  1. Empty-cell search on dense grids. Grid.select_random_empty_cell tried 50 random cells, then fell back to np.argwhere over the whole grid, on every call. On a 99% full grid that is 14 µs per call, and a Schelling model at that density spends most of its step there.

  2. Per-agent data collection. DataCollector built one closure call per reporter per agent, read agent.model.time through the observable descriptor for every agent, and called deepcopy on None and numpy scalars. About 390 ns per agent per step.

  3. Double-built views. Every select, shuffle, sort and groupby on model.agents built a strong-reference set and then rebuilt it as a weak one. Counting fully grown grass in Wolf-Sheep built a 10,000-entry weak dictionary to call len() on it: 2.2 ms of a 17 ms step.

  4. WeakKeyDictionary overhead. Its pure-Python wrapper and iteration guard made construction, membership and iteration about twice the cost of a dict keyed on weakref.ref objects.

  5. Unconditional property-layer writes. Every agent move wrote the empty layer twice through a numpy scalar index, even when the cell’s emptiness had not changed.

Two defects came out of the same pass:

  • Cell.get_neighborhood was decorated with functools.cache on a method, which is one global cache keyed on the cell. Discarding a grid left all its cells alive (10,000 cells after building and dropping fifteen 100x100 grids), and connect() on any cell cleared every cell’s cache in the process.

  • Grid.__init__ registered each grid’s private cell class in the global copyreg dispatch table, so a discarded grid stayed reachable from it.

Columnar agent state#

modelly.core.columns adds the one structural change with a large constant factor, as an opt-in. A Column declared on an agent class stores that attribute in a numpy array owned by the model (one table per concrete class, rows in insertion order, swap-remove on removal, the same scheme the continuous space uses for positions). The agent reads and writes its own row through a descriptor; the model reads everyone through model.columns[Cls].<name>, a zero-copy view.

The last two rows are the trade-off. A column attribute is a plain property installed on the class (the interpreter inlines property getters, which it never does for a custom descriptor) that reads the agent’s row through a memoryview, so a read returns a Python int, float or bool rather than building a numpy scalar, and arithmetic on it is Python arithmetic. That took a read from 79 ns to 27 ns and += 1 from 171 ns to 72 ns (CPython 3.15), and a Boltzmann exchange step over 5,000 column agents from 5.0 ms to 3.1 ms, against 1.6 ms with plain attributes. Dtypes a memoryview cannot index (strings, objects, complex, datetimes) keep numpy indexing, and a write a memoryview rejects (a float into an int column) falls back to numpy’s own assignment, so values and errors are unchanged. A column is still not the place for a scratch value read in a tight loop. where is bounded by building the AgentSet from 10,000 objects, not by the mask.

Recording a column with DataCollector is a straight slice of the table when the reporters are all columns of one class and the collected agents are that class’s whole population; rows are then in table order rather than registration order (identical until an agent is removed).

Continuous space#

get_agents_in_radius compares one point against every position, so a model where every agent asks for its neighbours is O(n²) per step. ContinuousSpace.neighbors_within(radius) builds one scipy.spatial.cKDTree from the positions as they are now and queries it for the whole population in a single call; on a torus the tree is periodic. A model uses it once per step and gives every agent the same snapshot of positions (a simultaneous update).

What changed, in order: the emit decorator’s wrapper checks for listeners inline and calls notify only when someone can hear; remove() uses try/except instead of a contextlib.suppress context manager (about 300 ns); the strong registry is a dict subclass, so membership, length and the registry writes run in C; Agent.__init__ and Agent.remove inline the registration when the model keeps the default register_agent and deregister_agent (a flag computed per class, with a test that an override is still honoured); the cooperative super().__init__() is skipped for plain subclasses; the listener test is four attribute reads with no dict lookups. FastRandom#

A quarter to a third of an agent-based model’s time is the standard library’s random, whose randint, choice, shuffle and sample are Python loops calling _randbelow per draw. modelly.FastRandom reimplements the four with the rejection loop written inline, making the same getrandbits calls in the same order, so a seed gives exactly the same numbers as random.Random (tested across seeds, sizes and both sample code paths). model.random is a FastRandom. The compiled core. Pure Python had nothing left to remove: what remained of a draw was the Python function call around a C call. modelly/_native/fastrng.c implements randint, choice, shuffle, sample and _randbelow in C as “fastcall” methods (the cheapest call CPython has). The type extends _random.Random and generates words from the same Mersenne Twister state the base class uses, so random(), gauss, getrandbits, seed and getstate from the standard library and the compiled methods consume one stream exactly as random.Random does; the stdlib’s sample set-size rule and both of its code paths are reproduced draw for draw. Anything outside the fast paths (ranges of 2³² or more, non-int arguments, sequences that are not lists or tuples, counts=) goes to the standard library’s own code, which reads the same state. At import a self-test compares a mixed sequence of draws with random.Random; on any mismatch, on free-threaded builds, without a compiler, or with MODELLY_PURE_PYTHON=1, FastRandom is the pure-Python PyFastRandom above. A second compiled module, modelly/_native/fastloop.c, runs do and shuffle_do on the model’s agent registries and the breadth-first walk behind Cell.get_neighborhood. A third, modelly/_native/fastcell.c, is the setter of CellAgent.cell: add to the new cell (capacity check, CellFullException), remove from the old one (AgentMissingException chained from the ValueError), and write empty only on a transition, through the normal attribute protocol so a grid’s property-layer empty still updates. Its twin is py_set_cell in modelly/_native/cells.py. A first version that used plain attribute lookups was no faster than Python 3.15’s specialised bytecode; the slot reads are what made the difference.

How we evaluate against other frameworks#

Micro-benchmarks say where time goes; whether a framework is faster for a researcher is decided on a real model. The method we use, and recommend for any comparison:

  1. Same model, same seeds. Take a research notebook written for the other framework and port it with python -m modelly.migrate, changing nothing but the framework API. Seed both from the same value so the random streams match.

  2. Prove equivalence before timing. Run both to completion and compare every output table by checksum. Only bit-identical outputs make the timings comparable; a port that changes the activation order or the random stream is a different model.

  3. Time CPU, pinned, alternating. Wall-clock on a shared machine swings by 2x; CPU time of the experiment cell, in-process, pinned to one core, with the two frameworks alternating for at least three rounds, is stable to a few percent. Keep every round, not only the best.

  4. Profile both and compare shares. The profiler inflates call-heavy code, so compare each function’s share of its own run, and attribute the remainder by bisection: swap one piece for a minimal stand-in and measure again.

Applied to a medfly population model written for Mesa 2.3 (21 cells, a 576-season factorial experiment, bit-identical output CSVs), the comparison went through two stages.

Stage one: the model’s own code. The profile put 68% of the time in the notebook’s model code, 25% in random and 7% in Modelly. Three changes to the model, identical in both notebooks and preserving the random stream (an early exit in the fruit status update placed after its random draw, len(self.slots) < capacity instead of two property hops, and re-filtering the free-fruit pool only on days when fruits were removed) cut the experiment cell by 3x on both frameworks: Modelly 30 s to 9.4 s, Mesa 26 s to 7.8 s, same checksums.

A third round of model-code changes, again identical on both sides and stream-preserving (an incremental rot score per fruit instead of a daily loop over its slots, an inlined capacity test in the egg-laying loop, FastRandom seeding on the Modelly side), took the experiment cell from 14.1 s to 11.2 s on Modelly and from 13.3 s to 11.0 s on Mesa, same checksums. Dispatching the 576 independent seasons of the factorial to a forked process pool, records reassembled in the original order so the CSV is identical, brings the cell to 1.3 to 1.6 s of wall-clock on eight workers: the largest practical gain on this workload, and the one that needs no re-validation of the model.

Stage two: the framework. Whole-cell rounds swing by up to 2x on a shared machine, so the comparison moved to a finer instrument: two persistent processes, one per framework, pinned to the same core, running the 576 seasons in 48 chunks with the order alternating, each chunk’s records hashed and compared (no mismatch in any run). Measured that way, the gap before this round was 2.1%, and none of it was in the model’s arithmetic:

  1. The random draws. FastRandom.randint had become 4% slower than the standard library on CPython 3.15, which now inlines Python-to-Python calls well; the operator.index calls were the difference. The table above lists the fixes; this was the largest item.

  2. Agent birth and death. One model flag (_quiet: default registry and nobody listening) replaces four attribute reads, and one class flag (_extra_hooks: columns or datasets) replaces two. The flag only ever turns false (on observe, observe_class, a batch, a suppress, or an overridden register_agent), so a stale value can only send an agent down the slower, still correct path. Creation went from 295 ns to 225 ns at the notebook’s live population, against 281 ns for Mesa.

  3. The garbage collector. About 11% of the run on both frameworks. Collecting identical garbage costs the same on both (78 to 83 ms per 240,000 objects); what differs is where collections fall relative to season boundaries, which depends on allocation counts. With the collection threshold set equally on both sides, Modelly is ahead at four of five values and behind at one. We report the default threshold. gc.freeze() after the imports would have given Modelly another 2.4%; applied to both sides it gives nothing, so it is a process setting rather than an engine property, and Modelly does not do it.

The playbooks: same model, each framework’s own idiom#

The port above answers “what does identical code cost”. The second question is what each framework lets a modeller write. benchmarks/playbooks/ holds eight models implemented twice, for Mesa 2.3 with per-agent methods on MultiGrid, SingleGrid, ContinuousSpace and NetworkGrid, and for Modelly with Column state, CellIndex (integer rows for the cells of any discrete space plus their sparse adjacency), Occupancy / claim, pairs_within / move_all, ColumnTable.thin and the DataCollector column reporters. The rules for a fair comparison, enforced by the runner:

  1. Same model: same rules, same phase order (synchronous, or one agent at a time in a random order), same parameters, same graph and initial positions where seeds can be shared; the Mesa side uses numpy where a Mesa modeller would.

  2. Agreement in distribution, checked: every implementation runs the same seeds and each summary statistic is compared with the Mesa reference by Welch’s t-test (flagged below 0.01). The implementations draw their random numbers in different orders, so the outputs differ run by run and must agree in law; vectorised_phases.md states why each vectorised phase has the law of its per-agent loop.

  3. Determinism, checked: the first seed runs twice per implementation. (This check caught the Mesa side being unseeded when the seed was passed positionally: Mesa 2.3 reads it from the keyword arguments in Model.__new__.)

  4. CPU time of a fresh interpreter per run, build and steps timed separately, pinned to one core, implementations alternating over three rounds, every round reported.

The “cell lists” column is the same model with Mesa’s data structure, every cell holding the list of its agents, so movement and predation stay per-agent loops: 1.4 to 1.9x, consistent with the port. The gap opens when the cell becomes a column of rows: the random walk is one random_neighbor call over the grid’s CSR adjacency, the exposure count a bincount, the predation a vectorised matching with the law of the shuffled sequential rule. Construction is reported separately (a 180x180 Moore grid builds in 0.11 s, a 30,000-node network in 0.4 s, against milliseconds for Mesa’s lazy structures); the build+run speed-ups in the results are correspondingly lower (26x, 6.7x, 38x, 10.5x, 4.3x, 191x, 9.2x, 6.9x, 27x).

The last three playbooks have phases that are sequential by nature, and each still has an exact array form (vectorised_phases.md, §7 to §9). Schelling’s unhappy residents move one at a time to random empty cells; since every move takes one empty cell and frees one, the pool of empty cells keeps its size, and all the moves become one sort over slots drawn up front. In the Boltzmann exchange, who gives in the random order is the least fixed point of a monotone map over the drawn order and partners, reached in a few array passes; the DataCollector slices the wealth column instead of visiting agents. In Sugarscape the foragers’ choices depend on the cells taken before their turn, so the walk to the first free cell stays a loop, but everything it reads (the visible cells, their sugar, the head of each forager’s ranking) is one array pass, and eating and starving move after the loop without changing the law. Rankings are not sorted up front: the loop takes a forager’s head when it is free and sorts the ranking only when that cell is not free at its turn (under a third of the turns). That gives the same runs, bit for bit, as sorting every ranking, and is 2.5x faster (median of 5 paired runs, range 1.9 to 2.6x, thread CPU time, large size, a loaded machine). The “cell lists” variants of these two are far ahead of Mesa (15x and 6.3x), unlike the 1.4 to 1.9x above: Schelling’s happiness count is an array pass even there, the empty-cell index answers each move in O(1) where Mesa’s move_to_empty draws until it hits an empty cell, and the Sugarscape scan reads cached neighbourhoods where Mesa’s select_cells builds whole-grid masks for every forager. These three were measured in a later session on another core (core 11, under the load of a shared machine), so compare their ratios rather than their seconds with the rows above; Sugarscape was measured again, all three variants, after the head-first walk (core 5, load average about 8 on 16 cores).

The insect playbook is a stage-structured population under sterile releases, an original model with the dynamics of the medfly workload (thousands of eggs a day, stage-specific mortality, density-dependent larval survival). Agent creation is at parity, so the individual-level gap is the per-agent loop only (4.3x). The cohort variant represents every insect in the same (stage, age, sex) class as one row and thins it with a binomial draw; it has the same law as the individual model (the agreement table shows it) and runs in 13 ms. The machine was under heavy load during these rounds; absolute times vary by up to 2x between sessions, the ratios do not.

Caches#

Two results are now reused instead of recomputed:

  • DataCollector.get_agent_vars_dataframe keeps the frame it last built and the number of steps it covered; a later call converts only the new steps and appends them. A dashboard that reads the frame every tick pays for one tick of rows instead of the whole history.

  • ContinuousSpace.neighbors_within keys its lists on the radius, the population size and a hash of the position array, so repeated queries within a step cost a hash of the positions (tens of microseconds for 10,000 agents) instead of a tree build, and any position change, including a direct write to the array, invalidates it.

Going meaningfully faster from here means the columnar state on the roadmap, not more micro-tuning.

Behaviour notes#

  • Seeded runs that call select_random_empty_cell on a dense grid draw from the index instead of from repeated random tries, so the sequence of chosen cells differs from earlier versions for the same seed. Runs are still fully reproducible for a given seed.

  • Iterating an AgentSet walks a snapshot: adding or removing agents while iterating no longer raises, and do/shuffle_do/map still skip agents removed earlier in the same pass.

  • select_random and select on model.agents now return a weak AgentSet like every other view (previously select_random leaked a strong-reference set).

What is next#

These are the changes with the largest remaining upside. Each is a project, not a patch.

  1. Vectorised movement on grids is in: a cell-row column plus CellIndex.random_neighbor moves a whole population in one call, and Occupancy / claim answer the per-cell questions a step still has. What remains is a visualisation path for agents that keep their cell as a column rather than in the cell’s list.

  2. Shared-memory replications. workers= runs replications in processes that each hold a full model; a shared column store would let a sweep over one large model fan out without copying it.

  3. Compiled hot loops. The neighbourhood lookup and do / shuffle_do on the model’s registries now run in modelly/_native/fastloop.c, and the cell move in modelly/_native/fastcell.c (7 to 14% on the cell-list playbooks). What remains per agent is the random-neighbour lookup around the draw and the property-layer empty setter.

python benchmarks/global_benchmark.py        # the four reference models, saves timings_N.pickle
python benchmarks/compare_timings.py a.pickle b.pickle
python benchmarks/playbooks/compare.py --core 5   # the eight playbooks against Mesa 2.3
