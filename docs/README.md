# Modelly documentation

The rendered site is <https://remipelloux.github.io/Modelly/>. It is built with Sphinx and
MyST from this folder and published by the `docs` GitHub Actions workflow: a push to `main`
updates `/dev/`, a release tag `vX.Y.Z` updates `/X.Y/` (and the root, when it is the newest minor).

## What is here

| Path | Content |
|---|---|
| `index.md` | the landing page |
| `getting_started.md` | concepts and the tutorial index |
| `tutorials/*.ipynb` | twelve executable notebooks, run during the build |
| `using_modelly_in_your_project.md` | from an empty folder to a tested, replicated model |
| `migrating_from_mesa.md` | construct-by-construct map and the codemod |
| `performance.md`, `vectorised_phases.md` | the performance audit, and the argument for vectorised step phases |
| `best-practices.md`, `overview.md` | guidance and the object model |
| `lint.md` | the rules of `python -m modelly.lint` |
| `profile.md` | `python -m modelly.profile` and `modelly.profile.Profiler` |
| `checkpoints.md` | `Model.save`, `Model.load` and `checkpoint_every` |
| `apis/*.md` | API reference, generated from docstrings by autodoc: one page per domain package (`core`, `space`, `time`, `data`, `behaviour`, `scenarios`, `batch`, `viz`) plus `log`, `migrate`, `lint` and `profile` |
| `examples.md`, `examples/` | generated at build time from `modelly/examples/` |
| `images/branding/` | the SVGs on the README, generated by `tools/branding/generate_assets.py` |
| `conf.py` | Sphinx configuration |
| `versioning.py` | the version switcher and old-version banner settings, read by `conf.py` |

## Build locally

```bash
pip install -e ".[docs]"
sphinx-build -b html docs docs/_build/html          # executes the tutorials (a few minutes)
MODELLY_NB_EXECUTION=off sphinx-build -b html docs docs/_build/html   # skip execution, quick
```

Open `docs/_build/html/index.html`. The `examples.md` page and the `examples/` folder are
regenerated on every build; do not edit them by hand, edit the `Readme.md` next to each example.

## Versions

The site serves the newest minor release at the root, `main` at `/dev/` and every minor
release at `/X.Y/`. The built HTML of every version is stored on the orphan branch
`docs-site`; each workflow run builds one version, puts it into that tree with
`scripts/assemble-docs-site.sh` (which also writes the root `switcher.json` the version
menu reads) and deploys the whole tree. Build one version as published:

```bash
bash scripts/build-docs-version.sh dev /tmp/docs-dev        # this checkout, as /dev/
bash scripts/build-docs-version.sh v1.1.0 /tmp/docs-1.1     # a tag, from a temporary worktree
```

Tags before 1.2 are built through `scripts/docs-overlay/conf.py`, which adds the switcher
to their own configuration.

One-time setup, before the first versioned deploy (run from the repository root):

```bash
git worktree add --orphan -b docs-site ../modelly-docs-site
bash scripts/build-docs-version.sh v1.0.1 /tmp/docs-1.0
bash scripts/build-docs-version.sh v1.1.0 /tmp/docs-1.1
bash scripts/assemble-docs-site.sh ../modelly-docs-site /tmp/docs-1.0 1.0
bash scripts/assemble-docs-site.sh ../modelly-docs-site /tmp/docs-1.1 1.1
git -C ../modelly-docs-site add .
git -C ../modelly-docs-site commit -m "docs(site): 1.0 and 1.1"
git push origin docs-site
```

Then, in the repository settings: under Environments, `github-pages`, allow deployments
from tags matching `v*` as well as `main`; keep Pages on the "GitHub Actions" source; and
exempt `docs-site` from any ruleset that blocks force pushes, since the workflow
force-pushes it as a single commit.

## Writing docs

Markdown everywhere, MyST syntax for directives. If you document a function, document the
parameters and the return value, and add a short example someone can paste into a notebook.
Tutorials must run top to bottom with the dependencies in `pip install -e ".[docs]"`.
