# Mesa vs Modelly — same notebook, same seeds

Runs the **identical** medfly ABM study (the optimized notebook, 662 seasons +
every figure) on two frameworks and compares wall-clock and output.

- **Mesa 2.3.2** — `mesa/Notebook_ABM_TIS_Optimise.ipynb` (the optimized
  notebook from `benchmarks/mesa_baseline/optimized/`).
- **Modelly** — `modelly/Notebook_ABM_TIS_Optimise_Modelly.ipynb`, generated by
  [`port_to_modelly.py`](port_to_modelly.py). Same parameters, experiments and
  seeds; only the framework API changes.

## The result

| | Mesa 2.3.2 | Modelly 1.2.0 |
| --- | --- | --- |
| Full notebook (all 21 cells) | **32.1 s** | **31.1 s** |
| Factorial experiment only (cell 7, 576 seasons) | **19.6 s** | **19.5 s** |
| Output CSVs | — | **bit-identical** |

**Modelly is ~1.03× the speed of optimized Mesa 2.3.2** on this workload, and
the two frameworks produce byte-for-byte identical CSVs (same seeds, same
`random.Random` stream), so the port is behaviourally exact.

Both venvs are pinned to the same analysis stack (numpy 2.5.4, pandas 3.0.6,
matplotlib 3.11.2, seaborn 0.13.2), so the comparison isolates the framework,
not the plotting libraries.

### What this benchmark measures (and what it doesn't)

The optimized notebook already removed the N+1 that made vanilla Mesa 2.3
quadratic (`Model.agents` rebuilt per agent). So this benchmark is *not*
"Modelly's AgentSet beats Mesa's WeakKeyDictionary". It is: given the same
optimized model code, what does each framework's core cost?

Modelly wins the simulation (cell 7) by a hair and wins the full notebook by
~3 %, with identical results. The two fixes that got it there were generic
framework changes, not notebook tweaks:

1. **`Model.time` was an `Observable` descriptor** — every `model.time` read
   (~165 000 per cherry season in this model) paid the descriptor protocol,
   ~3× a plain attribute. It is now a plain attribute; the CHANGED signal is
   emitted once per time advance via `_set_time()`. This speeds up *any* model
   that reads `time` in a loop.
2. **`@emit` called `notify` on every agent birth/death even with zero
   subscribers.** The emitted methods now short-circuit through
   `_maybe_notify`, and the per-registration debug logging was dropped.

For a workload dominated by millions of short-lived agent births/deaths, the
remaining per-agent cost (dual `_all_agents` + `_agents_by_type` registry,
reactive signals) is Modelly's deliberate richer-feature tax — it is now small
enough that the framework is at parity or ahead.

## Run it yourself

```bash
# regenerate the Modelly notebook from the Mesa one (optional, already done)
python benchmarks/mesaVSmodelly/port_to_modelly.py

# run both and write comparison.md
python benchmarks/mesaVSmodelly/compare.py
```

`compare.py` runs Mesa under `.venv-mesa2/bin/python` and Modelly under
`.venv/bin/python`, each in a clean directory (CSVs are deleted first, so the
full pipeline always runs). Results land in
[`results/`](results/) (`mesa.json`, `modelly.json`) and
[`comparison.md`](comparison.md).

## The port, in five rules

1. `import mesa` → `import modelly`; `mesa.Agent/Model/DataCollector` → `modelly.*`.
2. `super().__init__(model.next_id(), model)` → `super().__init__(model)`
   (Modelly assigns `unique_id` itself).
3. `Fruit_Agent` stays a plain object (FIX 6); its id comes from a new
   `model.next_fruit_id()`.
4. `model.agents_[Type]` → `model.agents` / `model.agents_by_type`
   (both are O(1) dict-backed).
5. `RematingModel.step` → `advance_day` (Modelly auto-advances `model.time`
   through an event schedule, which would shift the integer clock by one), and
   `self.random = random.Random(seed)` so the RNG stream is byte-identical to
   Mesa's `Model.__new__`.
