1.3.0: answers and trust#

Status: released as 1.3.0, with fixes in 1.3.1, 1.3.2 and 1.3.3 · Base: 1.2.0

1.3.0 is the release where Modelly stops being “a faster Mesa” and becomes the place a researcher goes to build, calibrate, explain, scale and publish an agent-based model, whatever their field. It is the largest release so far: 16 epics, 8 sprints, three public pre-releases. Everything in it works on Windows, macOS and Linux (see Platforms).

It stays backward compatible. Everything a 1.2 model uses keeps working; what 1.3 wants to change is deprecated with a warning and removed only in 2.0 (see Compatibility). That is why it is numbered 1.3.0 and not 2.0.0, even though it is a major release in scope.

Where we start#

What 1.2.0 already gives us, and what each piece unlocks for 1.3.0:

1.2.0 has

1.3.0 builds on it with

Scenario, seeded generators, run_batch / run_grid with one SeedSequence seed per run

Experiments, calibration and sensitivity analysis that are reproducible by construction

Checkpoints (model.save, Model.load, checkpoint_every), bit-identical resume

Time travel, resumable sweeps, run bundles for publication

Columns, CohortTable, CellIndex, three compiled modules (fastrng, fastloop, fastcell)

Free-threaded parallel phases, compiled select / agg, GPU arrays

modelly lint (16 rules), modelly profile (with --sizes), modelly migrate

lint --fix, editor integration, profile panels in Studio, modelly new

Solara, Altair and Matplotlib backends

Modelly Studio, publication figures, animations

Eight Mesa-vs-Modelly playbooks with agreement and determinism checks

A model zoo of validated reference models across research fields

Versioned docs (/dev/, /1.0/, /1.1/, /1.2/)

Domain tutorials, a course pack, a gallery

Wheels for Linux, macOS and Windows x86-64

Windows ARM64, free-threaded wheels

What 1.2.0 does not yet have, and researchers keep asking for:

  • A way to fit a model to data and say how good the fit is.

  • A way to say which parameters matter before spending a cluster budget.

  • A way to run large sweeps on a laptop, a workstation or a cluster with the same code.

  • A way to make a published result checkable by a reviewer in one command.

  • Real-world inputs: maps, census tables, road networks, contact matrices.

  • Agents that reason in language, without giving up reproducibility.

  • Ready-made, validated models for their own field, not only for the classic toy models.

Epics#

Every epic lists its goal, who it serves, the user stories, a sketch of the API, what “done” means, the tasks, and its dependencies. Sizes: S = under a sprint, M = one sprint, L = two sprints, XL = three or more. API sketches are proposals, to be settled in the epic’s first design review.

E1 · Calibration (modelly.calibrate)#

Goal: fit scenario parameters to observed data and report how good the fit is, with uncertainty, in a way that is reproducible run for run.

Platforms: pure Python and numpy; parallel runs use the E3 executors on every OS.

Serves: every applied field; epidemiology, ecology and economics first.

User stories

  • As an epidemiologist, I give weekly case counts and a prior on the transmission rate, and get a posterior distribution and a fit plot.

  • As an ecologist, I fit to several patterns at once (abundance, spatial clustering, age structure): pattern-oriented modelling.

  • As an economist, I fit by matching moments of simulated and observed series.

  • As anyone, I stop a calibration halfway and resume it tomorrow with the same result.

API sketch

from modelly.calibrate import ABCSMC, Prior, Target, distance

calibration = ABCSMC(
    model=Epidemic,
    priors={"beta": Prior.uniform(0.05, 0.5), "gamma": Prior.log_normal(-2, 0.5)},
    targets=[Target("infected", observed=cases, distance=distance.rmse)],
    steps=120,
    replicates=4,
    seed=2027,
)
posterior = calibration.run(budget=20_000, executor="processes")
posterior.summary()  # mean, median, HDI per parameter
posterior.plot()  # marginals, pairs, fit against data
posterior.to_dataframe()
calibration.save("calib.ckpt")  # resumable, uses checkpoints

Methods: ABC rejection; ABC-SMC with adaptive tolerances; simulated method of moments; Bayesian optimisation through an optional extra (modelly-abm[calibrate]); distances (RMSE, weighted, Wasserstein, custom); summary statistics from any DataCollector column.

Done when: ABC-SMC recovers known parameters of the bundled SIR and predator-prey models within the stated tolerance on three seeds; identical posterior for the same seed with the compiled core and the pure-Python twin; resumable from a checkpoint; docs page with a worked example; zoo model calibrated end to end.

Tasks

  • [ ] Design review: priors, targets, distances, posterior object (not recorded; moved to 1.4.0)

  • [x] ABC rejection over run_grid

  • [x] ABC-SMC with adaptive tolerance schedule and effective sample size

  • [x] Simulated method of moments

  • [ ] Bayesian optimisation adapter (optional dependency) (partly: a built-in Gaussian-process search, no adapter to an outside library; moved to 1.4.0)

  • [x] Posterior: summaries, HDI, plots, export

  • [x] Resume from checkpoint; parallel executors from E3

  • [x] Recovery tests on synthetic data; determinism tests

  • [x] Tutorial: calibrating an SIR model to case data

Size: L · Depends on: E3 (executors, results store), E4 (manifests)

E2 · Sensitivity analysis (modelly.sensitivity)#

Goal: tell the modeller which parameters drive which outputs, before and after calibration.

Platforms: pure Python and numpy; the emulator extra ships wheels for all three.

Serves: everyone with more than three parameters.

User stories

  • As a modeller with 12 parameters, I screen them cheaply and keep the 4 that matter.

  • As a reviewer, I see first-order and total Sobol indices with confidence intervals.

  • As a policy analyst, I see how an output’s uncertainty splits across inputs.

API sketch

from modelly.sensitivity import morris, sobol

screen = morris(
    Epidemic, space=scenario_space, output="peak_infected", trajectories=50, seed=1
)
screen.ranking()  # mu*, sigma per parameter
indices = sobol(
    Epidemic, space=scenario_space, output="peak_infected", samples=4096, seed=1
)
indices.plot()  # S1, ST with bootstrap intervals

Methods: one-at-a-time; Morris elementary effects; Sobol (Saltelli sampling, Jansen estimators); PAWN for skewed outputs; an optional Gaussian-process emulator so expensive models can be analysed from a few hundred runs.

Done when: Sobol indices match analytical values on the Ishigami function within the bootstrap interval; Morris ranking stable across seeds on the zoo models; plots and tables exportable; docs page and tutorial.

Tasks

  • [x] Parameter spaces shared with E1 and E3 (ScenarioSpace)

  • [x] OAT and Morris

  • [x] Sobol with Saltelli sampling and bootstrap intervals

  • [x] PAWN

  • [x] Emulator (optional extra)

  • [x] Verification on Ishigami and Sobol G functions

  • [x] Tutorial: which epidemic parameters matter

Size: M · Depends on: E3

E3 · Experiments and sweeps (modelly.experiments)#

Goal: one object that describes a study (parameter space, design, replicates, outputs) and runs it anywhere: a laptop, a workstation, a cluster.

Platforms: processes, threads, Dask and Ray on all three; process workers start with spawn on Windows and macOS, so models and reporters must be importable (new lint rule); SLURM and PBS submit from any OS to a Linux cluster.

Serves: research software engineers, anyone with a sweep bigger than one evening.

User stories

  • As a researcher, I describe a Latin hypercube over five parameters, 20 replicates each, and run it overnight; if the machine reboots, the sweep resumes where it stopped.

  • As an RSE, I run the same experiment on SLURM with one line changed, and get the same numbers as on my laptop.

  • As a student, I query results with SQL without loading everything into memory.

API sketch

from modelly.experiments import Experiment, designs

experiment = Experiment(
    model=Epidemic,
    space=ScenarioSpace(
        beta=(0.05, 0.5), gamma=(0.05, 0.3), vaccination=[0.0, 0.2, 0.4]
    ),
    design=designs.latin_hypercube(200),
    replicates=20,
    steps=365,
    outputs=["infected", "recovered"],
    store="runs/epidemic.parquet",
    seed=7,
)
experiment.run(executor="slurm", partition="short", max_parallel=500)
experiment.results().query("SELECT beta, avg(peak) FROM runs GROUP BY beta")

Designs: full factorial, Latin hypercube, Sobol and Halton sequences, custom lists. Executors: processes (today’s run_grid), threads (free-threaded Python, E11), Dask, Ray, SLURM job arrays, PBS. Store: Parquet files with a DuckDB view; one row per run and step.

Done when: the same experiment gives identical results on processes, threads and a local Dask cluster; a killed sweep resumes without repeating finished runs; SLURM executor tested on a container cluster in CI-local; docs page and RSE guide.

Tasks

  • [x] ScenarioSpace and designs

  • [x] Results store (Parquet plus DuckDB), schema, append-only writes

  • [x] Resume logic keyed by run seed

  • [x] Executors: processes, threads, Dask, Ray, SLURM, PBS

  • [x] Progress reporting and failure handling (retry, skip, record)

  • [x] Guide: running Modelly on a cluster

Size: XL · Depends on: E11 (threads), E12 (Parquet)

E4 · Provenance and reproducible publication#

Goal: every number in a paper can be traced to code, data, seed and environment, and re-run by a reviewer with one command.

Platforms: manifests store POSIX-style relative paths; hashes are taken over bytes; a bundle made on one OS verifies on the other two (tested).

Serves: authors, reviewers, journals, replication studies.

User stories

  • As an author, every run writes a manifest I can cite.

  • As a reviewer, I run modelly verify on the authors’ bundle and see “outputs match”.

  • As a lab, we archive a study on Zenodo with everything needed to rerun it.

  • As a modeller, I generate the skeleton of an ODD protocol description from my code.

API sketch

modelly run model.py:Epidemic --scenario scenario.toml --out runs/   # writes runs/manifest.json
modelly verify runs/manifest.json                                    # reruns, compares outputs
modelly bundle runs/ --out epidemic-study.zip                         # code, lock file, seeds, outputs
modelly odd model.py:Epidemic > ODD.md                               # ODD protocol skeleton

Manifest contents: code hash (git commit and dirty diff hash), Modelly version and build (compiled or pure), Python version, platform, dependency lock, scenario, seeds, input data hashes, output hashes, wall and CPU time.

Done when: a bundle made on Linux verifies on macOS and Windows; modelly verify reports the first differing output when one is changed; ODD skeleton covers the seven ODD elements; guide for journals and reviewers.

Tasks

  • [x] Manifest schema (versioned JSON) and writer

  • [x] modelly run command

  • [x] modelly verify with tolerance options for floating-point outputs

  • [x] modelly bundle (zip with lock file, Zenodo metadata, CITATION.cff)

  • [x] modelly odd generator from classes, scenario and schedule

  • [x] Guide: publishing a reproducible Modelly study

Size: M · Depends on: checkpoints (1.2), E12 (Parquet outputs)

E5 · Modelly Studio (modelly studio)#

Goal: one browser app to run a model, change parameters live, scrub through time, and see the profiler, the linter and the plots side by side.

Platforms: runs in the default browser on all three; tested in Chromium, Firefox, Safari and Edge; no OS-specific dependency.

Serves: everyone; the most visible feature of the release; teaching and demos.

User stories

  • As a modeller, I open modelly studio model.py:Epidemic, move a slider and watch the curve change.

  • As a teacher, I project Studio and scrub back to the step where the outbreak took off.

  • As a performance-minded user, I see which agent method takes the time while the model runs.

  • As a collaborator, I export the exact run I am looking at as a bundle (E4).

Views: space (grid, network, continuous, geographic), time series, histograms, agent table, parameter panel, timeline scrubber (E6), profiler panel, lint panel, run log.

Done when: every bundled example opens in Studio without code changes; scrubbing uses checkpoints and is instant on the examples; profiler and lint panels show live data; works offline; documented with screenshots.

Tasks

  • [x] Architecture decision: a Solara app reusing modelly.viz (see the decision below)

  • [x] Layout and parameter panel generated from Scenario

  • [x] Space views reusing the existing backends

  • [x] Timeline scrubber on checkpoints

  • [x] Profiler and lint panels

  • [ ] Export: figure, data, bundle (partly: figure, data, checkpoint and GIF export; bundle export moved to 1.4.0)

  • [ ] Docs and a short video (partly: the guide with screenshots; the video moved to 1.4.0)

Size: XL · Depends on: E6, E14, profiler and lint (1.1, 1.2)

Decision: Studio is a Solara app, not a separate front end. It reuses the portrayal styles, SpaceRenderer and the Matplotlib backend of modelly.viz instead of rewriting them in JavaScript, needs no front-end build on any OS, and keeps the model in the same Python process as the profiler, the linter and the recorder. The guide is Modelly Studio.

E6 · Time travel and run diff#

Goal: debugging a stochastic model without rerunning from step zero.

Platforms: the on-disk checkpoint ring writes through os.replace, atomic on all three and safe from Windows sharing violations.

User stories

  • As a modeller, I rewind to step 312, change one parameter, and replay from there.

  • As a maintainer, I diff two runs and see the first step and the first agent where they diverge.

  • As a researcher, I branch a run into several futures from the same state.

API sketch

from modelly.timetravel import Recorder, diff

with Recorder(model, every=10) as rec:  # checkpoints in memory or on disk
    model.run_for(1000)
past = rec.at(312)  # a model at step 312
past.scenario.vaccination = 0.3
past.run_for(100)
report = diff(run_a, run_b)  # first divergence: step, agent, attribute

Done when: rewind and replay are bit-identical with straight runs; diff finds a seeded divergence on every example; memory use bounded by a configurable budget.

Tasks

  • [x] In-memory and on-disk checkpoint ring with a memory budget

  • [x] Replay with modified scenario

  • [x] Branching runs

  • [x] Run diff on collected data, then on agent state

  • [x] Integration in Studio (E5)

Size: M · Depends on: checkpoints (1.2)

E7 · Language-model agents (modelly.llm)#

Goal: agents whose decisions come from a language model, with runs that stay reproducible and costs that stay under control.

Platforms: pure Python HTTP and a SQLite cache (standard library) on all three; local models through any HTTP endpoint.

Serves: computational social science, behavioural economics, anyone exploring generative agent models.

User stories

  • As a social scientist, I give each agent a persona and let it decide in natural language, then rerun the study and get the same decisions.

  • As a PI, I set a cost budget and the run stops before it exceeds it.

  • As a reviewer, the cached responses travel with the bundle (E4), so I can verify the study without calling any API.

Design

  • Provider-agnostic client with adapters for Anthropic, OpenAI-compatible endpoints and local models; no provider is required to install Modelly.

  • Deterministic response cache keyed on (model, prompt, parameters, agent seed); a cached run never calls the network; the cache is part of checkpoints and bundles.

  • Batching and concurrency limits; token and cost budgets per run; structured outputs validated against a schema.

  • Lint rule: an LLM call outside the modelly.llm client (unreproducible) is flagged.

Done when: a 200-agent opinion model runs, caches and replays offline bit-identically; budget stops a run cleanly; bundle verifies with no network; docs with an ethics and limitations section.

Tasks

  • [x] Client interface and adapters

  • [x] Cache store (SQLite) and cache keys

  • [x] Budgets, batching, retries

  • [x] Structured decisions with schema validation

  • [x] Lint rule MDL012 (network call outside the client)

  • [x] Example: opinion dynamics with persona agents

  • [x] Docs: reproducibility, cost, ethics

Size: L · Depends on: E4

E8 · Geospatial space (modelly.space.geo)#

Goal: start a model from real maps, census tables and road networks.

Platforms: GeoPandas, Shapely, pyproj and rasterio wheels on all three; no system GDAL; data scripts are Python, not bash.

Serves: urban studies, transport, ecology, epidemiology, archaeology, energy.

Features: vector space backed by GeoPandas (agents as points, polygons as cells); raster layers as property layers (optional rasterio); coordinate reference systems handled once, at the space; neighbourhoods by distance, contiguity or network; road networks from OpenStreetMap through an optional osmnx extra; export to GeoParquet and GeoJSON; Studio map view (E5).

Done when: a commuting model runs on a real city’s road network; a land-use model runs on a raster; both appear in the zoo with data download scripts and licences documented.

Tasks

  • [x] GeoSpace (vector) and RasterLayer

  • [x] CRS handling and spatial indices

  • [x] Road networks and routing

  • [x] Census-style initialisation helpers (synthetic populations from marginals)

  • [ ] Examples, data scripts, docs (partly: a synthetic-city example and the guide; real-data download scripts moved to 1.4.0)

Size: L · Depends on: E12 (GeoParquet), E14 (map view)

E9 · Networks: dynamic and multilayer#

Goal: social and contact structures as they really are: changing over time and on several layers at once (household, school, work).

Platforms: pure Python, numpy and scipy.

Features: temporal networks (edges with lifetimes); multilayer networks with per-layer weights; import from NetworkX, igraph and edge-list CSV; network collectors (degree distribution, clustering, component sizes) as cheap reporters; contact matrices for epidemiology.

Done when: an age-structured epidemic runs on a three-layer contact network; collectors match NetworkX on test graphs; adjacency updates are O(changed edges).

Size: M · Depends on: CellIndex adjacency (1.0)

E11 · Performance and scale#

Goal: the same model at ten times the population on the same machine, with results identical to today’s for a given seed; and real parallelism where the model allows it.

Platforms: free-threaded wheels for all three; Windows ARM64 wheels; GPU through CUDA on Linux and Windows and JAX on Metal or CPU on macOS; PGO measured per compiler.

Work items

  • Free-threaded Python (3.14t, 3.15t): make fastrng, fastloop and fastcell thread-safe; ship free-threaded wheels; run independent replicates on threads (E3).

  • Compiled AgentSet.select and agg: the next hot paths after cell moves, with Python twins and side-by-side tests, following fastloop.c.

  • GPU arrays for column phases: an array-API backend (CuPy, or JAX) for do_where, draw and CohortTable thinning, chosen by one setting; documented differences from numpy, if any.

  • Memory: agent memory footprint (slots for framework attributes, compact registries); target: half the bytes per agent of 1.2 on the playbooks.

  • Profile-guided wheels: PGO trained on the playbooks, kept only if measured faster.

  • modelly bench: run the playbooks locally and append to a history file; regression report before every pre-release, without paid CI runners.

  • Windows ARM64 wheels on a native ARM runner.

Done when: free-threaded wheels pass the full suite; compiled select and agg are faster than their twins on the micro-benchmarks and never slower on the playbooks; modelly bench history shows no playbook regression from 1.2.0.

Size: XL · Depends on: nothing; feeds E3

E12 · Data and interoperability#

Goal: Modelly data goes where researchers already work, and models come from where they already are.

Platforms: DuckDB and pyarrow wheels on all three; the NetLogo translator is pure Python.

Work items

  • Parquet and Arrow output from DataCollector (default for experiments), DuckDB queries, xarray for gridded time series.

  • NetLogo translator (modelly migrate --from netlogo): a skeleton Modelly model from an .nlogo file for the common primitives, with a report of what needs a human.

  • Mesa 3 adapter: run a Mesa 3 model’s agents inside Modelly for a comparison, in addition to the existing codemod.

  • R and Julia guides: reading Modelly outputs, calling Modelly from R through reticulate.

Done when: every example writes Parquet; the NetLogo translator handles the NetLogo models library’s wolf-sheep and fire models to a running skeleton; guides published.

Size: L · Depends on: nothing

E13 · Developer tools#

Goal: writing a correct, fast model is the easy path.

Platforms: LSP mode in VS Code, PyCharm and Neovim on all three; python -m modelly.dev gate replaces the bash-only gate for Windows contributors.

Work items

  • modelly new <name> --template grid|network|continuous|cohort|geo|llm: a seeded scenario, a determinism test, lint config, a Studio page, a README with the ODD skeleton.

  • modelly lint --fix and --diff for rules with a safe fix (MDL001, MDL002, MDL003, MDL009).

  • modelly lint --lsp: findings in VS Code, PyCharm and Neovim as you type; pre-commit hook.

  • New lint rules for 1.3 features: unseeded sampler in an experiment, network call outside modelly.llm, mutable default scenario fields, wall-clock in calibration targets.

  • Jupyter magics %modelly profile, %modelly lint; rich display of a Model.

  • Errors that name the agent, the step and the user’s line, not framework internals.

  • Type checking: the public API passes a strict type checker; py.typed kept accurate.

Done when: a new user goes from pip install to a linted, tested, profiled model in five minutes, timed with three volunteers; every fix is idempotent and tested.

Size: L · Depends on: lint and profile (1.1, 1.2)

E16 · Quality and release engineering#

Goal: a bigger release with fewer surprises than the smaller ones.

Platforms: the determinism suite runs on all three in CI; the release script is Python, not bash.

Sprint plan#

Eight sprints, in dependency order: a sprint is a unit of work, not a period of time, and the next one starts as soon as the previous one’s exit criteria hold. Each sprint ends with bash scripts/ci-local.sh green, the build matrix green on Windows, macOS and Linux, the docs building with -W, modelly bench showing no playbook regression, and a review note appended to this file.

  • [x] Works on Windows, macOS and Linux: the test runs in the build matrix on all three

Compatibility and the road to 2.0#

  • 1.3.0 is backward compatible with 1.2: every public name keeps working.

  • Checkpoints from 1.2 do not load in 1.3 (the format records the minor version). 1.3 adds a modelly checkpoint upgrade command for 1.2 files where the state maps cleanly.

  • Anything 1.3 wants to change raises a DeprecationWarning that names the replacement and the version that removes it (2.0).

  • 2.0 is where removals happen, after at least one minor release of warnings.
