Performance audit#

This page records how Modelly’s core data structures were audited, what was measured, what changed, and what is still on the table. Numbers come from the benchmark configurations in benchmarks/configurations.py (“large” sizes) and from micro-benchmarks run on the same machine, best of several alternating before/after runs, measured in CPU time.

The question#

Modelly keeps one Python object per agent and stores collections of them in dictionaries: AgentSet was a weakref.WeakKeyDictionary, the model registry is a plain dict, and a cell holds a list of the agents standing on it. Is that the right shape, and where does the time go?

The short answer: the shapes are right for the operations a simulation performs (ordered membership, O(1) removal, stable shuffles), but four things around them were costing far more than the containers themselves. Those were fixed. The one structural change with a large constant factor (columnar agent state) is a roadmap item, not a patch.

What the profile showed#

Profiling the four benchmark models at their “large” configuration put the framework’s own overhead in five places, in order of cost:

  1. Empty-cell search on dense grids. Grid.select_random_empty_cell tried 50 random cells, then fell back to np.argwhere over the whole grid, on every call. On a 99% full grid that is 14 µs per call, and a Schelling model at that density spends most of its step there.

  2. Per-agent data collection. DataCollector built one closure call per reporter per agent, read agent.model.time through the observable descriptor for every agent, and called deepcopy on None and numpy scalars. About 390 ns per agent per step.

  3. Double-built views. Every select, shuffle, sort and groupby on model.agents built a strong-reference set and then rebuilt it as a weak one. Counting fully grown grass in Wolf-Sheep built a 10,000-entry weak dictionary to call len() on it: 2.2 ms of a 17 ms step.

  4. WeakKeyDictionary overhead. Its pure-Python wrapper and iteration guard made construction, membership and iteration about twice the cost of a dict keyed on weakref.ref objects.

  5. Unconditional property-layer writes. Every agent move wrote the empty layer twice through a numpy scalar index, even when the cell’s emptiness had not changed.

Two defects came out of the same pass:

  • Cell.get_neighborhood was decorated with functools.cache on a method, which is one global cache keyed on the cell. Discarding a grid left all its cells alive (10,000 cells after building and dropping fifteen 100x100 grids), and connect() on any cell cleared every cell’s cache in the process.

  • Grid.__init__ registered each grid’s private cell class in the global copyreg dispatch table, so a discarded grid stayed reachable from it.

Columnar agent state#

modelly.core.columns adds the one structural change with a large constant factor, as an opt-in. A Column declared on an agent class stores that attribute in a numpy array owned by the model (one table per concrete class, rows in insertion order, swap-remove on removal, the same scheme the continuous space uses for positions). The agent reads and writes its own row through a descriptor; the model reads everyone through model.columns[Cls].<name>, a zero-copy view.

The last two rows are the trade-off. A column attribute is a plain property installed on the class (the interpreter inlines property getters, which it never does for a custom descriptor) that reads the agent’s row through a memoryview, so a read returns a Python int, float or bool rather than building a numpy scalar, and arithmetic on it is Python arithmetic. That took a read from 79 ns to 27 ns and += 1 from 171 ns to 72 ns (CPython 3.15), and a Boltzmann exchange step over 5,000 column agents from 5.0 ms to 3.1 ms, against 1.6 ms with plain attributes. Dtypes a memoryview cannot index (strings, objects, complex, datetimes) keep numpy indexing, and a write a memoryview rejects (a float into an int column) falls back to numpy’s own assignment, so values and errors are unchanged. A column is still not the place for a scratch value read in a tight loop. where is bounded by building the AgentSet from 10,000 objects, not by the mask.

Recording a column with DataCollector is a straight slice of the table when the reporters are all columns of one class and the collected agents are that class’s whole population; rows are then in table order rather than registration order (identical until an agent is removed).

Continuous space#

get_agents_in_radius compares one point against every position, so a model where every agent asks for its neighbours is O(n²) per step. ContinuousSpace.neighbors_within(radius) builds one scipy.spatial.cKDTree from the positions as they are now and queries it for the whole population in a single call; on a torus the tree is periodic. A model uses it once per step and gives every agent the same snapshot of positions (a simultaneous update).

What changed, in order: the emit decorator’s wrapper checks for listeners inline and calls notify only when someone can hear; remove() uses try/except instead of a contextlib.suppress context manager (about 300 ns); the strong registry is a dict subclass, so membership, length and the registry writes run in C; Agent.__init__ and Agent.remove inline the registration when the model keeps the default register_agent and deregister_agent (a flag computed per class, with a test that an override is still honoured); the cooperative super().__init__() is skipped for plain subclasses; the listener test is four attribute reads with no dict lookups. A three-day bisect at 2,800 agents on the medfly model below puts the current path at 11.4 ms against 11.7 ms for a stripped-down path with none of Modelly’s features and 11.2 ms for Mesa 2.3: the lifecycle is at parity.

FastRandom#

A quarter to a third of an agent-based model’s time is the standard library’s random, whose randint, choice, shuffle and sample are Python loops calling _randbelow per draw. modelly.FastRandom reimplements the four with the rejection loop written inline, making the same getrandbits calls in the same order, so a seed gives exactly the same numbers as random.Random (tested across seeds, sizes and both sample code paths). model.random is a FastRandom. The compiled core. Pure Python had nothing left to remove: what remained of a draw was the Python function call around a C call. modelly/_native/fastrng.c implements randint, choice, shuffle, sample and _randbelow in C as “fastcall” methods (the cheapest call CPython has). The type extends _random.Random and generates words from the same Mersenne Twister state the base class uses, so random(), gauss, getrandbits, seed and getstate from the standard library and the compiled methods consume one stream exactly as random.Random does; the stdlib’s sample set-size rule and both of its code paths are reproduced draw for draw. Anything outside the fast paths (ranges of 2³² or more, non-int arguments, sequences that are not lists or tuples, counts=) goes to the standard library’s own code, which reads the same state. At import a self-test compares a mixed sequence of draws with random.Random; on any mismatch, without a compiler, or with MODELLY_PURE_PYTHON=1, FastRandom is the pure-Python PyFastRandom above. Platform wheels carry the compiled modules (Linux glibc and musl on x86-64 and ARM64, macOS, Windows x86-64 and ARM64, the GIL and the free-threaded interpreters); other platforms install the pure wheel.

A second compiled module, modelly/_native/fastloop.c, runs do and shuffle_do on the model’s agent registries and the breadth-first walk behind Cell.get_neighborhood. Each loop has an identical pure-Python twin in modelly/_native/loops.py, used when the module is not built or MODELLY_PURE_PYTHON=1 is set; tests/native checks the two against each other.

A third, modelly/_native/fastcell.c, is the setter of CellAgent.cell: add to the new cell (capacity check, CellFullException), remove from the old one (AgentMissingException chained from the ValueError), and write empty only on a transition, through the normal attribute protocol so a grid’s property-layer empty still updates. It runs Cell.add_agent and remove_agent inline only when the cell’s type resolves them to Cell’s own (checked per type, revalidated on CPython’s type version tag, so an override or a later patch is called instead), and reads the _agents and capacity slots at their offsets. Its twin is py_set_cell in modelly/_native/cells.py. A first version that used plain attribute lookups was no faster than Python 3.15’s specialised bytecode; the slot reads are what made the difference.

Compiled event heap#

Every scheduled event (and every step, which is an event of the default schedule) went through heapq on Event objects, so each push and pop called Event.__lt__, a Python method, about log2(n) times. A fifth module, modelly/_native/fastevents.c, holds the event list’s heap: EventHeap runs heapq’s own sift steps, in the same order, on entries that carry the event’s time, priority and unique id, read once when it is pushed and compared as C numbers. That gives exactly what Event.__lt__ gives for an Event whose time is a float, a numpy float64 or an int of magnitude at most 2^53 (all exact as doubles); a subclass of Event, a Fraction time or a larger int is compared by calling < on the events, as heapq does. The twin, PyEventHeap in modelly/_native/events.py, is the previous list with heapq; tests/native/test_event_heap.py runs both on random schedules (ties, numpy times, huge ints, fractions, NaN, subclasses, cancellations, compactions) and checks every pop and the whole heap array after every operation. Both pickle through EventList as the events in heap order, the format of 1.3, so a checkpoint written with the compiled heap resumes under MODELLY_PURE_PYTHON=1 and the reverse (tests/native/test_event_heap_pickle.py, wolf-sheep resumed bit for bit). The keys are read at push: an event’s time and priority must not change while it is on a list, which they never could without breaking the heap.

Two changes around it, both in Python and both in the twin too: time advance asks the heap for the next event if it is due (pop_due) instead of popping the first future event and pushing it back, and schedule_event builds one weak reference to the callback instead of two (a WeakMethod costs about 0.5 µs); the event still refuses a callback that dies with the call.

Compiled column gather#

A DataCollector attribute reporter, AgentSet.get and agg read one attribute per agent through operator.attrgetter. For a Column attribute that calls its Python getter from C, a frame per agent, unless the collected agents are exactly one class’s whole table (then the column is sliced). fastset.attr_values now runs the getter’s three reads itself, agent._column_table._views[position][agent._column_row], for any agent whose class’s attribute is a Column property (the getter carries its position), caching each class’s position (revalidated on the class’s version tag) and its table’s view; any error runs the getter, which raises what it raises (ColumnMissingError for a removed agent). Plain attributes are read as before. The collector uses it one attribute at a time, mixed reporter sets included; the rows are identical (tests/native/test_column_gather.py, every dtype, interleaved classes, overridden and replaced properties, grown tables).

Profile-guided optimisation#

benchmarks/pgo.py builds the compiled modules twice from the same source: once with the build’s flags (-O3), once with GCC 16’s profile-guided optimisation (-fprofile-generate, a training run of every Modelly playbook at size small, the 17 core operations and an event-heavy schedule, benchmarks/pgo_training.py, then -fprofile-use), and times every Modelly playbook variant at size large in the two, paired as modelly bench --against does (7 rounds, pinned to core 3, results identical in every round, measured locally). The medians fall on both sides of 1 (0.993 to 1.003) and the interquartile ranges are within 1.5% of it, two of them entirely below 1 by at most 0.7% and one entirely above it by at most 0.5%: no playbook is measurably faster. What the compiled modules do per call is a handful of C operations around interpreter calls, and the branches a profile could reorder are already the predictable ones. The build does not use a profile, and hatch_build.py has no PGO option. Clang (which needs llvm-profdata merge between the two steps) and MSVC (/GL with /LTCG:PGINSTRUMENT and /LTCG:PGOPTIMIZE) were not tried: this machine has no MSVC, and the measurement above gives no reason to expect a different answer.

No variant is slower by the guard’s criterion; the largest median, Sugarscape’s 1.004, has its whole interquartile range within 1%. The playbooks are written with column phases and schedule no event but the step, so the event heap and the column gather have nothing to speed up in them; predator-prey in particular regrows its grass as a column, so it is not faster (the event-heavy wolf-sheep example above is). An earlier session that ran the checkout in a development interpreter with pyarrow installed measured the grid epidemic 2 to 4% slower; split into build and run, the difference was all in the run’s garbage collection, and with both sides in one interpreter it is 0.99 (20 rounds, IQR 0.96 to 1.03). That is why --against now runs both sides in the release environment’s interpreter.

The performance guard (python -m modelly.dev perf, 17 core operations, measured locally) finds no operation slower than 1.3.3: medians from 0.983 (creating and removing agents with columns) to 1.028 (creating and removing plain agents, IQR 0.994 to 1.034); the two neighbourhood walks read 1.016 and 1.019 with lower quartiles of 1.002 and 1.004, under the guard’s 3% threshold and on code this release does not change; schedule+run event reads 0.993, since its 500 events at distinct times make every heap comparison a single step.

Measured on Linux only: Windows and macOS could not be measured on this machine, so the claim “no playbook slower than 1.3.3” holds for Linux x86-64 and is untested elsewhere.

Memory-mapped columns#

modelly.core.storage decides where a table’s columns live. InMemory is the default and what 1.3 did. MemoryMapped(directory) keeps every numeric column in a numpy.memmap file in a fresh folder under directory; the operating system pages rows in and out, so a table can hold more rows than fit in memory, and a column that doubles is grown by extending its file, without copying the rows already written. Opt in with model.columns.storage = MemoryMapped(...) before the first agent of a class is created, or CohortTable(rng, storage=MemoryMapped(...), ...). The folder is deleted by close(), at the end of a with block, or when the storage is garbage-collected. Object columns cannot be mapped and stay in memory. A checkpoint (or any pickle) carries the rows, not the file names, and loading it copies them into a new folder under the same directory; since a checkpoint is built in memory, saving and loading one needs as much memory as its columns. tests/core/test_storage.py checks that a memory-mapped run holds the same rows as an in-memory one (agents growing past several doublings, and a cohort table of three million rows on disk), that checkpoints resume bit for bit in a new folder, and that the folder goes.

A row of a ColumnTable belongs to an Agent object, which stays in memory (225 bytes with its registry entries, “Memory per agent” below, before its row attributes), so a hundred million agents need over 22 GB for the objects alone, whatever the columns’ storage. A hundred million rows do fit as a CohortTable, rows without objects. benchmarks/large_columns.py builds one (count, stage, age, patch and a float trait per row, 19 bytes) and runs a stage-structured life cycle on it: binomial thinning by stage, ageing, stage transitions and offspring draws.

The run, measured locally: 100 million rows (2.55 GB of columns at the table’s capacity of 2^27 rows), three steps, each in its own systemd scope with a hard limit and no swap (systemd-run --user --scope -p MemoryMax=... -p MemorySwapMax=0); “cgroup peak” is the scope’s memory.peak, which counts the mapped file pages it holds as well as anonymous memory. Free-threaded CPython#

All four modules load on free-threaded CPython (wheels for 3.14t and 3.15t; tested on 3.15t) and declare Py_MOD_GIL_NOT_USED, so importing Modelly leaves the GIL off; before 1.3 they refused to load and the pure twins ran instead. What each one does to be safe:

  • fastrng: every draw holds the generator’s per-object critical section, the lock _random.Random’s own methods take, so a draw from C and a random() from the standard library never interleave on one state. A list being shuffled, sampled or chosen from is locked with it. Draws from one generator shared by threads are atomic (tested: the threads together draw exactly the serial sequence, in some order), but which thread gets which number depends on scheduling: give each thread its own model, or its own generator.

  • fastloop: list items are read as new references; a cell’s connections dict is walked inside its critical section.

  • fastcell: the per-type layout cache is per thread; bind() and its readers share one PyMutex; slots are read through getattr and list.remove runs itself, since both take the object’s lock.

  • fastset: list items are read as new references; weak-reference keys are snapshotted with PyDict_Keys, which locks the dict.

GIL builds compile the same code with the locks as empty blocks (modelly/_native/ftcompat.h); paired micro-benchmarks of shuffle, randint, choice, sample, the cell move, do and the neighbourhood walk against main were within noise (medians 0.92 to 0.98). On CPython 3.15t (Linux x86-64) the whole suite passes with the compiled modules, and tests/native/test_threads.py (four threads; shared draws, independent replicates on threads equal to serial runs, agents moved across a shared grid, select and agg while another thread adds and removes agents) passed 25 repeated runs at ten times its default rounds. ThreadSanitizer was not run: it needs an instrumented interpreter.

fastevents (1.4) holds the heap’s critical section in every method and declares Py_MOD_GIL_NOT_USED; the column gather in fastset reads items as new references and type version tags with relaxed loads. Both were built and tested on the GIL interpreter only: the machine they were written on has no free-threaded CPython, so the 3.15t build of these two is untested.

How we evaluate against other frameworks#

Micro-benchmarks say where time goes; whether a framework is faster for a researcher is decided on a real model. The method we use, and recommend for any comparison:

  1. Same model, same seeds. Take a research notebook written for the other framework and port it with python -m modelly.migrate, changing nothing but the framework API. Seed both from the same value so the random streams match.

  2. Prove equivalence before timing. Run both to completion and compare every output table by checksum. Only bit-identical outputs make the timings comparable; a port that changes the activation order or the random stream is a different model.

  3. Time CPU, pinned, alternating. Wall-clock on a shared machine swings by 2x; CPU time of the experiment cell, in-process, pinned to one core, with the two frameworks alternating for at least three rounds, is stable to a few percent. Keep every round, not only the best.

  4. Profile both and compare shares. The profiler inflates call-heavy code, so compare each function’s share of its own run, and attribute the remainder by bisection: swap one piece for a minimal stand-in and measure again.

Applied to a medfly population model written for Mesa 2.3 (21 cells, a 576-season factorial experiment, bit-identical output CSVs), the comparison went through two stages.

Stage one: the model’s own code. The profile put 68% of the time in the notebook’s model code, 25% in random and 7% in Modelly. Three changes to the model, identical in both notebooks and preserving the random stream (an early exit in the fruit status update placed after its random draw, len(self.slots) < capacity instead of two property hops, and re-filtering the free-fruit pool only on days when fruits were removed) cut the experiment cell by 3x on both frameworks: Modelly 30 s to 9.4 s, Mesa 26 s to 7.8 s, same checksums.

A third round of model-code changes, again identical on both sides and stream-preserving (an incremental rot score per fruit instead of a daily loop over its slots, an inlined capacity test in the egg-laying loop, FastRandom seeding on the Modelly side), took the experiment cell from 14.1 s to 11.2 s on Modelly and from 13.3 s to 11.0 s on Mesa, same checksums. Dispatching the 576 independent seasons of the factorial to a forked process pool, records reassembled in the original order so the CSV is identical, brings the cell to 1.3 to 1.6 s of wall-clock on eight workers: the largest practical gain on this workload, and the one that needs no re-validation of the model.

Stage two: the framework. Whole-cell rounds swing by up to 2x on a shared machine, so the comparison moved to a finer instrument: two persistent processes, one per framework, pinned to the same core, running the 576 seasons in 48 chunks with the order alternating, each chunk’s records hashed and compared (no mismatch in any run). Measured that way, the gap before this round was 2.1%, and none of it was in the model’s arithmetic:

  1. The random draws. FastRandom.randint had become 4% slower than the standard library on CPython 3.15, which now inlines Python-to-Python calls well; the operator.index calls were the difference. The table above lists the fixes; this was the largest item.

  2. Agent birth and death. One model flag (_quiet: default registry and nobody listening) replaces four attribute reads, and one class flag (_extra_hooks: columns or datasets) replaces two. The flag only ever turns false (on observe, observe_class, a batch, a suppress, or an overridden register_agent), so a stale value can only send an agent down the slower, still correct path. Creation went from 295 ns to 225 ns at the notebook’s live population, against 281 ns for Mesa.

  3. The garbage collector. About 11% of the run on both frameworks. Collecting identical garbage costs the same on both (78 to 83 ms per 240,000 objects); what differs is where collections fall relative to season boundaries, which depends on allocation counts. With the collection threshold set equally on both sides, Modelly is ahead at four of five values and behind at one. We report the default threshold. gc.freeze() after the imports would have given Modelly another 2.4%; applied to both sides it gives nothing, so it is a process setting rather than an engine property, and Modelly does not do it.

The playbooks: same model, each framework’s own idiom#

The port above answers “what does identical code cost”. The second question is what each framework lets a modeller write. benchmarks/playbooks/ holds eight models, each implemented for Mesa 2.3 with per-agent methods on MultiGrid, SingleGrid, ContinuousSpace and NetworkGrid, for the current Mesa 3.5 with its cell spaces (OrthogonalMooreGrid, CellAgent, Network), its experimental continuous space and AgentSet.shuffle_do, as in Mesa’s own examples, and for Modelly with Column state, CellIndex (integer rows for the cells of any discrete space plus their sparse adjacency), Occupancy / claim, pairs_within / move_all, ColumnTable.thin and the DataCollector column reporters. The rules for a fair comparison, enforced by the runner:

  1. Same model: same rules, same phase order (synchronous, or one agent at a time in a random order), same parameters, same graph and initial positions where seeds can be shared; the Mesa side uses numpy where a Mesa modeller would.

  2. Agreement in distribution, checked: every implementation runs the same seeds and each summary statistic is compared with the Mesa reference by Welch’s t-test (flagged below 0.01). The implementations draw their random numbers in different orders, so the outputs differ run by run and must agree in law; vectorised_phases.md states why each vectorised phase has the law of its per-agent loop.

  3. Determinism, checked: the first seed runs twice per implementation. (This check caught the Mesa side being unseeded when the seed was passed positionally: Mesa 2.3 reads it from the keyword arguments in Model.__new__.)

  4. CPU time of a fresh interpreter per run, build and steps timed separately, pinned to one core, implementations alternating over ten rounds, every round reported.

The Mesa 3.5 implementations agree with Mesa 2.3’s: over 100 paired seeds all 40 summary statistics are equivalent within half a standard deviation, and no test falls below 5% (paper/data/agreement_small_baselines_summary.json, which also holds the mesa-frames variants); flocking, the network and the insects draw the same numbers in the same order and reproduce Mesa 2.3 run for run. Where a phase searches cells one agent at a time (Sugarscape’s foragers), every implementation uses the same single-pass loop. Median CPU seconds of the steps at the large size, all variants in one session, ten rounds, pinned to a performance core (CPU 2, performance governor, turbo disabled, so the core runs at its fixed 1.9 GHz base frequency; every per-round ratio is within 15% of its median). Mesa 3.5 is itself faster than Mesa 2.3 on five playbooks (1.3x to 3.1x), about as fast on Sugarscape (1.02x) and flocking (1.00x; both use mesa.space.ContinuousSpace, which runs it 1.6x faster than Mesa 3.5’s experimental continuous space) and slower on predator-prey (0.91x). mesa-frames (development branch, commit ef92326, polars 2.0 on one thread) is 2.1x to 6.5x faster than Mesa 2.3 on three of its four playbooks and slower on Sugarscape (0.71x); Modelly columns are 3.0x to 9.4x faster than mesa-frames. One thread is mesa-frames’ better setting here: with all of polars’ threads it is slower on three of the four workloads (grid epidemic 1.73 s against 1.52 s, Boltzmann wealth 2.61 s against 1.46 s, Sugarscape 4.29 s against 2.96 s) and faster only on Schelling (2.12 s against 2.90 s; paper/data/frames_threads.json).

The hand-vectorised Mesa 3.5 baseline is faster than Modelly’s columns: 4.4x on the epidemic, 1.8x on Schelling, 2.8x on Boltzmann wealth. It is the same arithmetic without the agents: Modelly keeps an Agent per individual, with its identity, its step() and the agent-set API, and that bookkeeping is the difference. It agrees with Mesa 2.3 in distribution (paper/data/agreement_small_mesa3np_summary.json; one statistic, Schelling’s segregation index, differs by 0.24 sd, p = 0.045 after Holm).

The last three playbooks have phases that are sequential by nature, and each still has an exact array form (vectorised_phases.md, §7 to §9). Schelling’s unhappy residents move one at a time to random empty cells; since every move takes one empty cell and frees one, the pool of empty cells keeps its size, and all the moves become one sort over slots drawn up front. In the Boltzmann exchange, who gives in the random order is the least fixed point of a monotone map over the drawn order and partners, reached in a few array passes; the DataCollector slices the wealth column instead of visiting agents. In Sugarscape the foragers’ choices depend on the cells taken before their turn, so the walk to the first free cell stays a loop, but everything it reads (the visible cells, their sugar, the head of each forager’s ranking) is one array pass, and eating and starving move after the loop without changing the law. Rankings are not sorted up front: the loop takes a forager’s head when it is free and sorts the ranking only when that cell is not free at its turn (under a third of the turns). That gives the same runs, bit for bit, as sorting every ranking, and is 2.5x faster (median of 5 paired runs, range 1.9 to 2.6x, thread CPU time, large size, a loaded machine). Schelling’s “cell lists” variant is far ahead of Mesa 2.3 (14x) because its happiness count, three quarters of Mesa’s run, is an array pass even there; Mesa’s move to a random empty cell already runs in constant expected time. Sugarscape’s is not (1.3x): it runs the same single-pass search as both Mesa versions. (An earlier Mesa 2.3 Sugarscape built a whole-grid mask per forager with select_cells; the cached neighbourhood gives the same runs, bit for bit, 4 to 5x faster, and is what Mesa’s own example does.)

The insect playbook is a stage-structured population under sterile releases, an original model with the dynamics of the medfly workload (thousands of eggs a day, stage-specific mortality, density-dependent larval survival). Agent creation is at parity, so the individual-level gap is the per-agent loop only (5.7x over Mesa 2.3, 3.2x over Mesa 3.5). The cohort variant represents every insect in the same (stage, age, sex) class as one row and thins it with a binomial draw; it has the same law as the individual model (the agreement table shows it) and runs in 11 ms. Absolute times vary by up to 2x between sessions on a shared machine; the ratios much less.

The modelly-gpu variant of the grid epidemic (benchmarks/playbooks/grid_epidemic/modelly_gpu.py) is the column variant modelly with its step on CuPy: the same agents and grid, the columns as a DeviceTable, the adjacency as a DeviceCellIndex, the draws from a PhiloxStream (GPU arrays). Measured by benchmarks/playbooks/gpu_speedup.py at 10 million agents on a 1000 x 1000 torus (ten agents per cell; the playbook’s density would need 16 million Python cell objects), 60 steps, seed 1. Raw numbers: benchmarks/playbooks/results/gpu_speedup.json.

Machine. A laptop: Intel Core Ultra 7 356H, 30 GB, and an NVIDIA GeForce RTX 5050 Laptop GPU (8 GB, driver 615.78, CUDA runtime 13.2 from the cupy-cuda13x 14.2.0 wheel); numpy 2.5.4. Shared with other jobs: every run was started through a guard that lets one heavy job run at a time, but the load from lighter work was not controlled and the CPU frequency was not pinned.

Method. A fresh interpreter per run, the two variants alternating; the wall clock around the 60 steps with the device synchronised before each reading (a GPU’s time is not the process’s CPU time); the build (agents, grid, upload) timed apart. One untimed GPU run first fills CuPy’s kernel cache.

About 350 ms per step on one CPU core against 10 ms on the GPU. The building is the same Python work for both (10 million Person agents) and dominates a 60-step run: build plus steps is 1.5 to 1.7x faster on the GPU (Python 3.15 rounds). The 10x target of the 1.4.0 roadmap is met on this mid-range laptop GPU for the steps; it is not a claim about construction, which the GPU does not touch.

Equality. gpu_speedup.py --equality ran modelly-gpu with the same seed on numpy (69 s: the numpy fallback computes Philox numbers with array operations) and on CuPy (1.9 s, kernel compilation included): the infected series of the 60 steps is identical and so is the SHA-256 of the final state, days and row columns of all 10 million agents. The test suite checks the same on every backend that loads (tests/gpu), JAX with 64-bit types included. Against the CPU column variant, which draws from model.rng, the agreement is in distribution, as for every playbook variant.

Where the GPU does not pay. At the playbook’s own large size (20,000 agents) the steps take 0.17 to 0.21 s on CuPy against 0.11 s for the CPU column variant (3 seeds each): kernel launches and synchronisations cost more than the arithmetic. The insect cohorts on a DeviceCohortTable take 1.9 to 2.1 s for 120 days against 10 ms for the host CohortTable (3 seeds): the table has fewer than two hundred rows. Both variants run on CuPy because the roadmap asks that they do, and give the numpy run’s integers there; neither is a reason to use a GPU. Apple Metal (JAX) was not measured: no Apple GPU was available.

Caches#

Two results are now reused instead of recomputed:

  • DataCollector.get_agent_vars_dataframe keeps the frame it last built and the number of steps it covered; a later call converts only the new steps and appends them. A dashboard that reads the frame every tick pays for one tick of rows instead of the whole history.

  • ContinuousSpace.neighbors_within keys its lists on the radius, the population size and a hash of the position array, so repeated queries within a step cost a hash of the positions (tens of microseconds for 10,000 agents) instead of a tree build, and any position change, including a direct write to the array, invalidates it.

The remaining per-agent framework cost in the grid models is about 0.6 µs of a 1.4 µs agent-step (the cell move, the neighbourhood lookup, the shuffle and the membership check); the rest is the agent’s own logic. Going meaningfully faster from here means the columnar state on the roadmap, not more micro-tuning.

Behaviour notes#

  • Seeded runs that call select_random_empty_cell on a dense grid draw from the index instead of from repeated random tries, so the sequence of chosen cells differs from earlier versions for the same seed. Runs are still fully reproducible for a given seed.

  • Iterating an AgentSet walks a snapshot: adding or removing agents while iterating no longer raises, and do/shuffle_do/map still skip agents removed earlier in the same pass.

  • select_random and select on model.agents now return a weak AgentSet like every other view (previously select_random leaked a strong-reference set).

What is next#

These are the changes with the largest remaining upside. Each is a project, not a patch.

  1. Vectorised movement on grids is in: a cell-row column plus CellIndex.random_neighbor moves a whole population in one call, and Occupancy / claim answer the per-cell questions a step still has. What remains is a visualisation path for agents that keep their cell as a column rather than in the cell’s list.

  2. Shared-memory replications. workers= runs replications in processes that each hold a full model; a shared column store would let a sweep over one large model fan out without copying it.

  3. Compiled hot loops. The neighbourhood lookup and do / shuffle_do on the model’s registries now run in modelly/_native/fastloop.c, the cell move in modelly/_native/fastcell.c (7 to 14% on the cell-list playbooks), and select, agg and the weak views in modelly/_native/fastset.c. What remains per agent is the random-neighbour lookup around the draw and the property-layer empty setter.

How to re-run#

python benchmarks/global_benchmark.py        # the four reference models, saves timings_N.pickle
python benchmarks/compare_timings.py a.pickle b.pickle
python benchmarks/playbooks/compare.py --core 5   # the eight playbooks against Mesa 2.3

modelly bench runs the Modelly variants of the playbooks on every operating system without shell tools, keeps a history and reports regressions. Run it from the repository root (or point --playbooks at the directory):

modelly bench --label v1.2.0                       # record a named baseline (size large, 3 rounds)
modelly bench --baseline v1.2.0                    # compare; exit 1 on a regression above 10%
modelly bench --size small --rounds 5 --only grid_epidemic --only schelling:modelly
modelly bench --history ~/bench/modelly.jsonl --core 3 --threshold 0.05
MESA_PYTHON=.venv-mesa2/bin/python modelly bench   # the Mesa variants too
modelly bench --against 1.3.3 --rounds 7 --core 3  # this checkout against a release, paired

--against VERSION (or release, the last tag) builds that release from its tag in this repository with the performance guard’s builder (same compiler, same numpy, pandas, scipy and networkx, cached in .modelly-bench/), then runs every Modelly variant once per side per round, the side order swapped every round, with the same seed. Both sides run in the release environment’s interpreter, the checkout’s with the checkout first on PYTHONPATH, so both import the same third-party packages: run from a development environment that has pyarrow installed, the checkout imported it and the release did not, which added about 10,000 objects for the garbage collector and moved where its collections fall (the grid epidemic’s 60 steps spend more time collecting than computing). The two runs must give identical results; the report gives each variant’s median per-round CPU ratio and its interquartile range, and exits 1 when a variant’s median is above 1 + --threshold and even its lower quartile is above 1 (the performance guard’s criterion), or when results differ. Nothing goes to the history.

Each variant runs in a fresh interpreter; the order of the variants alternates from one round to the next. Runs are pinned to one core through psutil (pip install modelly-abm[bench]) on Linux and Windows; macOS has no CPU affinity API, and the report says the runs were not pinned. Every invocation appends one JSON line to the history file (.modelly-bench/history.jsonl by default): the Modelly version, which compiled modules were active, Python, platform, pinning, and every round’s CPU seconds per variant. The baseline is the entry named by --baseline (a --label, or an index such as 0 or -2), else the latest entry at the same size.
