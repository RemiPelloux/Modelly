1.4.0: scale out and connect#

Status: in release: every epic merged except F10 Studio II (in progress), release gate pending · Base: 1.3.3

1.3.0 lets a researcher answer a question with a model. 1.4.0 removes the ceilings on how big that model can be and how close to the real world it can run: distributed populations, GPU and differentiable models, live data and assimilation, multi-scale coupling, and Modelly running in a browser tab. Eleven epics, eight sprints, three pre-releases, all on Windows, macOS and Linux (see Platforms). Backward compatible with 1.3.

F1 · Distributed simulation (modelly.distributed)#

Goal: one model whose population and space are split across processes or machines, with the same results as a single-process run for the same seed.

Platforms: MPI through mpi4py (Open MPI or MPICH on Linux and macOS, MS-MPI on Windows); a Dask and a Ray backend that need no MPI and run on all three.

User stories

  • As an epidemiologist, I run a 30-million-agent country model on 64 cores of a cluster with the code I wrote for 100,000 agents on my laptop.

  • As an RSE, I check that a distributed run and a single-process run of a small model give the same output, byte for byte.

Design

  • Spatial partitioning (grid blocks, graph partitioning for networks, k-d partitioning for continuous space) with ghost cells (halo exchange) at partition borders.

  • Agents migrate between partitions when they move; migration happens at a phase boundary, in a deterministic order.

  • Random numbers: one stream per agent (from the agent’s seed), so results do not depend on how the space is partitioned.

  • Collectors reduce across partitions; checkpoints write one file per partition plus an index.

API sketch

from modelly.distributed import Cluster, partition

with Cluster(backend="mpi", workers=64) as cluster:
    model = cluster.build(Epidemic, scenario, partition=partition.grid_blocks(8, 8))
    model.run_for(365)
    cluster.collect().to_parquet("runs/country.parquet")

Done when: partition-independent results on the zoo’s grid and network models (2, 4 and 16 partitions, identical outputs); weak scaling efficiency of at least 70% from 1 to 64 workers on the grid epidemic playbook; runs on MPI and Dask on all three platforms.

Done: partly. Byte-identical reporters and agent states at 1, 2, 4 and 16 partitions on grid, network and continuous reference models (the zoo has no agent-level grid or network model), on the local backend, under mpirun -n 2 and -n 4, and on Dask with 2 workers. Weak scaling on one 16-core laptop is 62% at 2 workers, 20% at 8 and 9% at 16 (independent copies of the same work already fall to 24-32% there), so the 70% target at 64 workers could not be measured. Ray is untested, and macOS and Windows were not run: hosted CI now runs only the Release and docs workflows.

Tasks

  • [x] Per-agent random streams (opt-in in 1.4, default in 2.0)

  • [x] Partitioners: grid blocks, graph (METIS-style, pure Python fallback), k-d (grid blocks in S1; graph: BFS banding plus greedy boundary refinement, not METIS; k-d: recursive bisection)

F2 · GPU backend, generally available#

Goal: column phases, cohorts and cell spaces run on a GPU with one setting, with results equal to numpy within documented tolerances.

Platforms: CUDA through CuPy on Linux and Windows; JAX on Linux, Windows (CPU or CUDA) and macOS (Metal where available, CPU otherwise). Every GPU path has a CPU fallback.

Work items: array-API backend for every column operation; CellIndex adjacency, counts and random-neighbour draws on the GPU; CohortTable binomial thinning on the GPU; counter-based random streams (Philox) so GPU and CPU draw the same numbers; memory planner for populations larger than GPU memory (batches); benchmark playbooks with a modelly-gpu variant.

Done when: grid epidemic and insect cohorts playbooks run on CUDA and Metal; results equal the CPU run for integer state and within a stated tolerance for floats; at least 10x faster than the CPU column variant at 10 million agents on a mid-range GPU (measured and published, not assumed).

Done: partly. The grid epidemic at 10 million agents on CuPy keeps the numpy run’s integer state bit for bit and runs its 60 steps 34x faster than the CPU column variant on a laptop RTX 5050 (the build is not faster, so 1.5x to 1.7x including it); at the playbook’s own 20,000 agents the GPU is slower. The insect cohorts run on CuPy with the numpy run’s integers but 200x slower: under 200 rows, so launch overhead dominates. Metal is untested (no Apple GPU). Backends numpy, CuPy and JAX, Philox streams identical on all three, batches for populations larger than the GPU, modelly-gpu playbook variants.

Size: L · Depends on: 1.3 E11 preview

F3 · Differentiable models (modelly.diff)#

Goal: gradients of model outputs with respect to parameters, for gradient-based calibration and sensitivity, where the model allows it.

Platforms: JAX on all three (CPU everywhere, GPU per F2).

Design: column phases traced with JAX; discrete random choices handled with documented estimators (straight-through, Gumbel-softmax, score function) and an explicit warning that the gradient is an approximation; a differentiable flag per phase; gradient checks against finite differences.

User stories: as an economist, I fit 40 behavioural parameters with gradient descent in minutes instead of an ABC run of days; as a modeller, I get local sensitivities (gradients) at the calibrated point for free.

Done when: gradient-based calibration recovers known parameters on two zoo models; gradients agree with finite differences within tolerance; docs explain when gradients are meaningful and when they are not.

Done: yes. Gradient calibration recovers 0.0305 and 0.379 for the Bass model’s 0.03 and 0.38 (straight-through) and 1.448 and 0.937 for Bouchaud-Mezard’s 1.5 and 1.0 (pathwise; the gap is the noise of the observed Gini series, 1.54 and 1.09 with four replicates); the finite-difference checks pass with a relative error below 1e-4; docs/differentiable.md says when a gradient means something. JAX is the optional diff extra.

Size: L · Depends on: F2, 1.3 E1

F4 · Modelly in the browser (Pyodide and WebAssembly)#

Goal: run a Modelly model and Studio entirely in a browser tab, with no installation, and share it as a link or a static page.

Platforms: any OS with a current browser (Chrome, Edge, Firefox, Safari); Pyodide build of the pure wheel in 1.3 (smoke test), compiled modules built for WebAssembly in 1.4.

Work items: Emscripten builds of fastrng, fastloop, fastcell; a modelly export-web command that writes a static site (model code, scenario, Studio) deployable on GitHub Pages; optional dependencies trimmed for the browser; worker threads for long runs; size budget for the first load.

Done when: every 1.3 example runs in the browser from a static export; the export of a zoo model loads in under 10 seconds on a typical connection (measured); the docs gallery embeds live models.

Done: partly. All 14 examples and the 12 zoo models of its base run from a static modelly export-web site in headless Chromium, with the pure wheel and the Emscripten-compiled one; the five zoo models merged after it are run by the browser stage of the release checks. A scipy-free zoo model is ready in 8.0 s on a 50 Mbit/s line, but one that needs scipy takes 12.3 s and “Fast 4G” takes 21.4 s: Pyodide, numpy and pandas alone are 13.5 MB. The gallery embeds three live models.

Size: L · Depends on: 1.3 E5 Studio

F5 · Live data and data assimilation (modelly.stream)#

Goal: feed real-world observations into running models and keep an ensemble of runs close to reality: the core of a digital twin.

Platforms: pure Python on all three; MQTT and Kafka connectors as optional extras with wheels for all three.

Design: stream sources (files, HTTP polling, MQTT, Kafka); observation operators mapping model state to observed quantities; ensembles of replicates advanced in lock step; assimilation by particle filter (resampling replicates through checkpoints) and ensemble Kalman filter for continuous parameters; a live dashboard in Studio.

User stories: as a public-health modeller, I update tomorrow’s forecast every morning from yesterday’s cases; as a transport researcher, I keep a traffic model in step with loop-detector counts.

Done when: a nowcasting tutorial with a synthetic “truth” run shows the filter tracking it; particle resampling is reproducible for a seed; Studio shows the ensemble band live.

Done: partly. The nowcasting tutorial’s filter tracks a synthetic truth with an error of 5.07 people against 69.2 for the unfiltered ensemble, the ensemble Kalman filter recovers beta 0.451 for 0.45, and a run is bit-identical for a seed with the compiled and the pure-Python core. The live band in Studio is F10’s. MQTT and Kafka sources are tested against fakes only.

Size: L · Depends on: 1.3 E6 (checkpoint ring), E3

F6 · Multi-scale coupling (modelly.couple)#

Goal: couple agents to continuous processes: system-dynamics stocks and flows, ODEs, and PDE fields over space.

Platforms: numpy and scipy on all three.

Design: a Field type (a property layer with a solver: diffusion, advection, decay) stepped on its own time step; ODE and stock-flow components through scipy’s integrators; a coupling schedule (who reads what, when) checked for consistency at build time.

Done when: an ecology model with a diffusing nutrient field and a disease model coupled to a hospital-capacity ODE are in the zoo, with conservation checks (mass balance) as tests.

Done: yes. nutrient_foragers and hospital_epidemic are in the zoo; fields conserve mass to round-off, a Gaussian matches the heat kernel, the hospital stock-flow ODE is within 1e-6 of its matrix-exponential solution, and checkpointed runs resume bit for bit. Fields are limited to orthogonal grids with uniform spacing; advection is first-order upwind.

Size: M · Depends on: 1.3 E8 (rasters)

F7 · Emulators, active learning and history matching#

Goal: answer questions about expensive models with far fewer runs.

Design: Gaussian-process and neural emulators trained on experiment results (1.3 E3); active-learning designs that choose the next runs where the emulator is least certain; history matching (implausibility measures, waves of non-implausible space), widely used in epidemiology and climate science.

Done when: history matching reproduces a published wave sequence on a zoo model; active learning reaches the same emulator accuracy as a Latin hypercube with at most half the runs on two benchmarks.

Done: partly. History matching on the age SEIR keeps 17.1%, 4.4%, 3.1% and 2.5% of the box over four waves, with the truth inside each. Active learning against a Latin hypercube saves a factor of 1.3 to 2.7 on the Bass model (2 at most run counts) but only 1.1 to 1.4 on Branin and 0.8 to 1.4 on Ishigami, where a well-spread design is already close to best; the tests assert the measured factors.

Size: M · Depends on: 1.3 E1, E2, E3

F8 · Synthetic populations (modelly.population)#

Goal: realistic starting populations from aggregate data, with households and places.

Design: iterative proportional fitting and combinatorial optimisation from census marginals; households, schools and workplaces assigned with distance constraints; contact networks generated from places; privacy notes and no bundled personal data.

Done when: a synthetic population for a sample region reproduces its marginals within tolerance; the age-structured SEIR zoo model starts from it.

Done: yes. About 20,000 people across 41 Burlington census tracts from made-up marginals: totals and age counts exact in every tract, sex counts off by fewer than 3, no school or workplace over capacity or beyond its distance limit; the age SEIR starts from it (scenario_from_population) and follows its final-size relation within 0.05.

Size: M · Depends on: 1.3 E8, E9

F9 · Performance II#

Work items: compiled event scheduler (heap in C, same ordering); compiled DataCollector gather for column-backed agents; memory-mapped columns for populations larger than RAM; per-compiler PGO (GCC, Clang, MSVC) shipped where it measures faster; modelly bench comparison against 1.3 on all three OSs.

Done when: no playbook slower than 1.3 on any OS; event-heavy models (wolf-sheep) measurably faster; a 100-million-row column run on a 16 GB machine.

Done: partly. No playbook slower than 1.3.3 on Linux x86-64 (medians 0.986 to 1.004, results identical); the wolf-sheep example runs at 0.95, 600 regrowth events per step at 0.70 and the column gather at 0.47. The predator-prey playbook is not faster (0.998 to 1.003): it schedules no events and regrows grass as a column. A 100-million-row cohort table peaks at 3.6 GB under a 16 GB limit (3.2 GB memory-mapped under a 3 GB limit). PGO measured 0.993 to 1.003 against -O3 and is not shipped. Windows, macOS and the free-threaded build were not measured.

Size: L

F10 · Studio II#

Work items: ensemble views (bands across replicates); experiment browser over the results store; calibration and assimilation dashboards; map and network views at scale (WebGL); recording a session as a reproducible script.

Status: in progress. The ensemble, assimilation, experiment, analysis and map tabs and the browser checks in Chromium, Firefox and WebKit are on its branch, not yet merged.

F11 · Quality and platforms#

Work items: partition-independence and GPU-equality suites in the determinism suite; WebAssembly in the release matrix; distributed tests on a three-OS MPI matrix (MS-MPI on Windows); deprecations for 2.0 announced in this release’s notes.

Done: partly. Partition independence is in the determinism suite and the 2.0 changes are announced (docs/deprecations.md, warnings on the moved geo names). The Pyodide smoke test, the three-OS MPI matrix and the cross-OS bundle check exist as manual-only workflows and were not run: hosted CI runs only the Release and docs workflows, and scripts/release-checks.sh runs their Linux parts locally. GPU equality is checked in tests/gpu (numpy against CuPy and JAX), not in the determinism suite.

Open questions#

  • [x] Default distributed backend: MPI (fastest on clusters) or Dask (easiest everywhere)? Neither is a default: Cluster(backend=...) names local, mpi, dask or ray, and only local needs nothing installed. MPI needs the distributed extra and a launcher; the guide says when to pick each.

  • [x] Per-agent random streams: opt-in in 1.4 and default in 2.0, or default already in 1.4? Opt-in in 1.4 (S1), so 1.x models keep their numbers.

  • [x] JAX as an optional extra only, or part of rec for GPU users? Optional extras only: diff (JAX) and gpu (CuPy); rec stays network and viz, and import modelly loads neither.

  • [x] Which public data sets to use for the synthetic-population tutorial (licences)? Made-up marginals on real Burlington census tracts (public domain), OpenStreetMap streets (ODbL) and ESA WorldCover (CC BY 4.0), as small bundled samples with NOTICE.md; nothing personal.
